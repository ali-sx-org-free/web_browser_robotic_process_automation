Manual acceptance on one computer

Before a PR is merged, run the management portal, the test site, a command-line Recorder and several workers on one computer, and check each item in the task record's acceptance steps. The production server, its data and paired apps are left alone.

This method checks features and screens. Packaged apps, the network between two computers, workers on Windows and the headless Linux bundle are covered by CI's end-to-end tests and checked again with a draft release before publishing (see What this method can't check).

When to use it

  • Before merging a PR. The task record's "Manual acceptance (suggested steps)" says what to look at; this page says how to set up the environment on one computer. Three states are recorded separately: code merged, automated tests passed, manual acceptance passed (Status and acceptance records).
  • Several stacked PRs at once. When each PR is branched from the previous one, the top branch contains all of them; merge them in order.
  • A Mac is easiest. A Linux desktop or Windows works too with the same commands (paths and how to find the LAN address differ on Windows).

Preparation

Branch, dependencies, a new folder
cd ~/code/web_browser_robotic_process_automation
git fetch origin
git switch the-branch-to-check
git pull --ff-only
git log -1 --oneline      # must match the latest commit on the PR page
uv sync --locked          # required when dependencies changed (M8 added cryptography)

Use a new folder for each acceptance, for example ~/rpa-m8-check, holding the portal's data (data) and the work folders of the Recorder and each worker. Only a new folder creates "Test site automation" and imports the example scenarios on first start; to start over midway, stop the portal, delete data and start again.

Acting as several computers and several people

  • Another computer. Open the portal with this computer's LAN address (macOS: ipconfig getifaddr en0, or en1 when that prints nothing) and the server treats the requests as coming from another computer. For example, M8's "the first system administrator can only be created on the server": http://LAN-address:8080 shows only an explanation, http://127.0.0.1:8080 can create it. The portal must be started with --host 0.0.0.0.
  • Several users (sign-in is required from M8). Sign in with one account in a normal browser window and another in a private window; use another browser for a third. Normal windows of one browser share the sign-in, and so do different ports on 127.0.0.1 (8080 and the Recorder address), so the Recorder address is usually already signed in; to see "signing in through a Recorder" open the Recorder address in a private window.
  • The same account signed in "somewhere else". Keep a cookie of its own with curl: curl -c file -H 'Content-Type: application/json' -d '{"username":"…","password":"…"}' http://127.0.0.1:8080/login, then curl -b file …/api/me to see whether that sign-in still works (for example, it should end after a password change).
  • Two workers. Windows 4 and 5 in the table above.
  • An old worker or portal. Window 6 in the table above. For an upgrade test, run the old portal on other ports (for example --port 8090 --worker-port 8091) with another --data to create the data, stop it, then start the new version with the same --data; the old portal can run without --no-local-worker, so runs happen inside the portal and nothing needs pairing.

Restarts and upgrades

  • Press Ctrl+C in window 2 to stop the portal, then ↑ and Enter to start it with the same command. Workers and the Recorder lose the connection briefly and retry; their pairing is kept in their work folders, so no new invitation is needed.
  • The test site in window 1 is not affected. A run half-way through finishes on its worker, and the portal collects the result once it is back.
  • Switching code (for example from main to the branch under test) is the same: stop it, then start from another folder or after switching branches with the same --data; tables are migrated on start.

Recording the results

  • Each step states what you should see; when it doesn't match, note the address, the run or batch ID (run-…, batch-…) and the screen.
  • Hand the results to the responsible agent to fill in the task record's "Verification and review" and "Later entries": version (commit), environment (computer, operating system), which steps were done, the results and what was not checked. Not done, skipped and cancelled do not count as passed (AGENTS.md).
  • Also note documentation that doesn't match the program (for example a different button name).

Cleaning up

  1. Press Ctrl+C in each window to stop the portal, the test site, the Recorder and the workers.
  2. If you used a worktree, run git worktree remove ~/rpa-xx-check/main-code in the clone, then delete the whole ~/rpa-xx-check.
  3. git switch main.

Common problems

What you seeWhat to do
8080, 8081 or 8765 is in useThe production server or the previous acceptance is still running. Stop it, or use --port 8090 --worker-port 8091 (the invitation and Agent API addresses change accordingly).
"Test site automation" has fewer cards than expectedThe folder isn't new, or the program comes from another branch. Stop the portal, delete data, check git branch --show-current and git log -1, then start again.
The docs don't match the portal, or the newest ADRs are missingYou opened an old worktree or another branch. Check the path in the address bar. The portal, the Recorder and the workers use that code too, so restart all of them after switching to the right branch.
A device never shows "Online"Look for errors in its window; if the invitation expired, create a new one on the Devices page. In a window with RPA_WORKER_TOKEN set, run unset RPA_WORKER_TOKEN first.
A run or batch stays "Queued"The location is "This computer" (there is no local worker with --no-local-worker), or the workers are offline.
Two rows don't run at the same timeBoth workers must be online and idle; also check "Rows queued at once across all batches" above the batch list.
The browser for step debugging or recording doesn't open on the RecorderYou used 127.0.0.1:8080 instead of the address the Recorder printed.
You keep being sent to the sign-in page, or switching accounts changes another window too (M8)Normal windows of one browser share the sign-in; use a private window or another browser for another account.
An account is paused from signing in (M8, five wrong passwords)Wait 15 minutes, or restart the portal (the pause is kept only in the running portal).

What this method can't check

  • Packaged apps. Installing RPA Recorder and RPA Worker, the first-start download and updates: CI's "Desktop build" runs end-to-end tests on the packaged apps on macOS and Windows, and before publishing, a draft release is installed once on a real computer (Remote workers).
  • The network between two computers. Firewalls, LAN addresses, the external port: see Deployment & operations.
  • Headless Linux servers. Installing and upgrading the bundle is checked by CI's "Server bundle" job on Rocky 8; upgrade production as described in Dev environment › Bundle.
