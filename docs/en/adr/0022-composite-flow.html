ADR 0022: Composite conditions live on connections, running at once uses different workers, and repeats are a fixed count

Flow between the nodes of a composite scenario (DAG): a connection checks an output of its source node to decide whether it is followed, and nodes no connection leads to are skipped; ready nodes can be queued together and picked up by free workers; a node can repeat a fixed number of times, and downstream nodes use the outputs of the last time. Scheduling is worked out again from the node results each time; skips and counts are not stored separately.

Context

M6 composite scenarios are DAGs: they fork and join, run one node after another in topological order and stop on failure. The MVP prototype also showed parallel nodes, conditional branches and repeat counts; these were left out on purpose and listed as open work. Conditions and loops inside a scenario became DSL blocks in M7.1 (ADR 0021); flow between nodes is a different problem, because it decides on the outputs published by upstream nodes rather than on the page.

All nodes of a composite run used to go to the worker that picked up the first node, and each worker runs one browser at a time, so nodes that were ready together still ran one by one.

Decision

  • Conditions live on connections. A connection may have when (one output of the source node: equals, notEquals, in, empty) or otherwise (none of the source's other conditional connections holds). Once all of a node's upstream nodes have finished, it runs if at least one connection led to it and is skipped otherwise; the skip carries on downstream. An output binding counts as an unconditional connection; when a drawn connection joins the same two nodes, its condition applies.
  • Running at once uses different workers. The definition's concurrency (1–10, default 1) is how many ready nodes may be queued together. Above 1, nodes are no longer tied to the first worker; they stay on one worker only when a worker was chosen, when continuing from a failed node, or when a node uses a file output of an upstream node. The worker and the desktop app do not change; a worker still runs one browser at a time.
  • Repeats are a fixed count. A node's repeat (1–20) runs it that many times one after another; each time is a run of its own and must pass, and downstream nodes use the outputs of the last time. When continuing from a failed node, a node stopped partway through its repeats carries on from the time that did not pass.
  • Scheduling is worked out from the results. rpa_core.workflow.advance works out from each node's state and outputs which nodes can start, which are skipped and whether the run is finished. The server works it out again on every notification, so a repeated notification never queues a node twice and a restart can carry on.
  • Stop on failure as before. Once a node does not pass, no further nodes are queued; nodes already running at the same time finish first. A skip by condition is not a failure, and the publishing gate does not compare skipped nodes that did not run.
  • Version 2 only. The three fields are only accepted in version 2 (DAG); definitions that do not use them keep the same JSON and hash.

Consequences

  • Running at the same time needs several workers (two rpa worker processes on one computer count as two). With a single worker the behaviour is the same as before.
  • Nodes on different workers do not share a workspace; nodes handing over files through file outputs stay on the same worker, and files shared in any other way are not guaranteed to be there.
  • The replay joins nodes in node order; nodes that ran at the same time are not played side by side, and a repeated node plays its last time, with the other times opened from the node details.
  • A validation record only proves the branches taken that time; branches that were not taken need their own validation with data that leads to them.
