ADR 0027: The server manages the RPA Python runtime's packages, and Workers get them from the server

System administrators add and remove the packages Python nodes can use in the admin console. The server resolves one lock file and downloads each wheel once from the fastest source; Workers fetch the missing files over the LAN and build the same package environment on the interpreter bundled with the App. No App needs reinstalling.

Context

RPA Python runtime 1.0.0 is Python 3.13.14 plus 9 packages (18 with dependencies: openpyxl, xlsxwriter, xlrd, pandas, python-dateutil, python-docx, pypdf, charset-normalizer, requests). The list lives in the repository's runtimes/python/requirements.in; CI builds and self-tests it for four platforms and bundles it with the Worker App and the Linux server package. On Workers pip is removed and EXTERNALLY-MANAGED is in place, so nothing else can be installed.

Today one more package means changing the repository, bumping the runtime's minor version and shipping a release. The archive's file name is part of the runtime ID (ADR 0018), so every Worker and the server must be reinstalled from the full installer.

Download speed is a real problem. The company network reaches PyPI slowly: on 2026-10-20 the server's uv sync was slow enough that mirror speed tests were added (scripts/setup-linux.sh); on 2026-10-21 browser downloads measured about 0.8–1.7 MiB/s from the official source and about 5 MiB/s from a mirror in China. The default packages' wheels add up to about 30–36 MB per platform (PyPI on 2026-11-27: about 30 MB on Windows, 34 MB on macOS, 36 MB on Linux x64); adding scikit-learn adds about 23–45 MB per platform (numpy is already there).

Goals

  • System administrators add and remove packages in the admin console; after publishing, every Worker uses the new packages automatically.
  • The defaults are today's 9 packages, identical to the bundled runtime; without changes, behavior and downloads stay the same.
  • Adding packages is fast: one download from the internet, from the fastest source, only what's new; Workers fetch over the LAN and prepare while idle.
  • Every Worker has the same packages and versions, and earlier versions can be restored.
  • Workers don't reach the internet; no App or server package needs reinstalling.

Decision

Admin console (system administrator)
  add / remove ─▶ draft ─▶ check: uv resolves pylock.toml → wheels for every platform → download from the fastest source → import on the server
                                                                                  │
                                                                     publish: packages #N (immutable)
                                                                                  │
Server wheel store (by sha256, shared across versions) ◀── each file downloaded from the internet once ──┘
  │  Worker API: list and files for this version and platform (LAN, resumable, at most 4 Workers at once)
  ▼
Worker: bundled runtime (interpreter + default packages) + missing wheels ─▶ package environment venv (#N) ─▶ Python node
  • Interpreter and packages are separate. The RPA-Python-1.0.0-<platform>.tar.gz bundled with Apps and the server package stays and is extracted to the cache on first use as before, but it only serves as the interpreter and a source of the default packages. Python nodes actually run in a "package environment": a standard venv created from the bundled interpreter (no pip, without the bundled site-packages) containing exactly the packages of this package version. Subprocesses a script starts with sys.executable run in the same environment.
  • The package list lives on the server. One per runtime major version (only 1 today), stored in the server's database and shared by all Workers (D1). On first start the server creates "packages #1" from the default list and lock file shipped with the code, identical to the bundled runtime. Adding and removing edit a draft; after the checks pass it's published as #2, #3, …; published versions never change.
  • The server resolves once. uv pip compile --universal --only-binary :all: --python-version 3.13 writes a PEP 751 pylock.toml: each package's exact version and each wheel's URL, size, upload time and sha256. The previous lock file is the starting point, so adding a package keeps the other versions (tested with uv 0.11.32 on 2026-11-27: after adding tabulate, numpy, pandas and xlsxwriter kept their locked versions); upgrades happen only with "Check for updates". The server downloads a pinned uv from the package source the first time it's needed (version and sha256 in the code, D7).
  • Wheels only, for every platform. No source distributions: neither the server nor Workers compile or run installers. For each of the four platforms (windows-x86_64, macos-arm64, linux-x86_64 glibc 2.28, linux-aarch64) the server checks every package has a usable wheel; when one is missing it says which platform, and the package can be limited to the platforms it supports (a platform marker, e.g. pywin32 only on Windows). Scenarios that use it must declare platforms, and validation warns about it (tested on 2026-11-27: pywin32 without a marker gets locked for every platform, so the separate check is needed).
  • Files are kept on the server. Wheels are stored by sha256 under python-packages/ in the server's data directory and shared across versions; Workers only fetch from the server (Worker API) and never reach the internet.
  • Dispatch and reports. Tasks carry the package version. Among Workers that can run a task, those that already prepared this version go first. Others prepare it in the run's "runtime" phase (not counted against the deadline, per ADR 0020). The python section of result.json gains packages: package version, lock file hash, reused or prepared now, and how much was downloaded.

Download speed

ApproachEffect
One download from the internetThe server is the only place that downloads from outside; each file (identified by sha256) is downloaded once and every Worker fetches it over the LAN. Adding a 40 MB package for 50 Workers downloads "40 MB × platforms in use" from the internet, not 2 GB.
Use the fastest sourceThe package source defaults to "auto": PyPI, Tsinghua, USTC, Alibaba Cloud, Tencent Cloud and Huawei Cloud (the same list as scripts/setup-linux.sh) each download the same file with a known sha256; the fastest one with matching content goes first and the others become fallbacks in speed order. Results are shown on the page and reused for 24 hours. A specific source, a company Nexus/Artifactory/devpi URL, an HTTP proxy and a company root certificate can also be set (D3).
Changing sources can't change contentThe lock file records sha256. For a mirror, files.pythonhosted.org in the file URL is replaced with the mirror's same path; files are checked after download, and a mismatch is discarded and the next source tried, with the original URL last.
Only the platforms in useThe server downloads only for platforms that have devices (its own and those reported by paired Workers); a new platform is filled in when its first device comes online.
Only what's newAdding a package downloads only it and its new dependencies; unchanged versions aren't downloaded again. Packages with the same name and version as in the bundled runtime are copied from it on the Worker: the default #1 needs no downloads on Workers, and adding scikit-learn doesn't download numpy again.
Parallel and resumableThe server downloads 4 files at once (configurable); large files resume from where they stopped using HTTP Range; the page shows each file's progress, speed and source. Workers' downloads from the server are resumable too.
Prepare after publishingIdle Workers download and build a new version in the background without taking task time; the server limits how many Workers download at once (4 by default, configurable) so they don't saturate its network together.
Warn about big packagesBefore adding, the page shows the download size per platform and an estimate based on the current source's speed; a single package over 100 MB (e.g. PyTorch) needs another confirmation, with how much more disk each Worker will use.

Admin console: "Python packages"

A new page in the admin console, visible only to system administrators (like users and the audit log).

  • Current packages. Packages added directly: name, requested version, actual version, platforms, size per platform, license, summary, who added it and when; defaults are marked "Default". Dependencies are collapsed and show what needs them.
  • Add. Enter a name, optionally with a version constraint (e.g. tabulate, pandas>=3,<4), optionally limited to platforms. The page first shows the latest version, summary, license, home page, upload time and whether each of the four platforms has a wheel and its size, then adds it to the draft.
  • Remove. Takes it out of the draft; dependencies nothing else needs go with it, and those still needed stay with an explanation. The .py files of runtime-mode scenarios in every domain (published and draft) are scanned with ast to list the scenarios that import the package; when a published scenario uses it, removal is blocked by default and needs a reason to force it (D2).
  • Check. Resolve, check platforms, download (with progress), build on the server's own platform and import every directly added package; list the differences from the current version (added, removed, changed versions, including dependencies) and the download size per platform.
  • Publish, history, restore a version. Restoring publishes a new version with that version's lock file; the files are still there, so it's quick.
  • Device readiness. For the current version each Worker is "Ready", "Downloading N%", "Failed (reason)" or "App too old"; the Devices page under Cluster shows it too.
  • Settings. Package source and speed-test results, proxy, cooldown days (D4), how many Workers download at once, how many versions to keep.

Package environments on Workers

<cache>/python/
  1.0.0-windows-x86_64/     bundled runtime
  wheels/<sha256>.whl       downloaded wheels
  envs/<hash>-<platform>/   package environments (venv)

The bundled runtime is extracted as before (interpreter + default packages); wheels/ holds wheels from the server, named by content and shared across versions; envs/ holds one standard venv per package version, named by the lock file hash, with the same hash in .ready.

  1. Get this version's list for this platform from the server: packages, versions, wheel file names, sha256, sizes.
  2. Packages with the same name and version in the bundled runtime are copied using the dist-info RECORD (hard links on the same disk); the rest are downloaded from the server into wheels/ and checked against sha256.
  3. Create the environment from the bundled interpreter with the standard library's venv (no pip, without the bundled site-packages). On Windows this uses the venvlauncher.exe shipped with python-build-standalone (confirmed present in the 3.13.14 Windows build on 2026-11-27).
  4. Unpack the wheels with the standard library (purelib, platlib and data per the wheel format, no console scripts), compile them with compileall, then import every directly added package in the new environment.
  5. Write .ready and rename to the final folder. Only one process builds a given version at a time (the existing lock file); on failure the folder is discarded and rebuilt next time.

The latest 3 versions and any in use are kept and the rest deleted, along with files in wheels/ that kept versions no longer use. The Runner runs the interpreter in envs/… with the same flags as before (-E -s -B -X utf8).

Versions and consistency

  • A package version is one lock file. Exact versions plus every file's sha256; every Worker builds the same packages and versions, differing only in platform binaries. Pages show "packages #N", counting up on each server; the lock file hash compares across servers.
  • Scenario files don't change. They still say runtime: "1" and don't name a package version.
  • One run, one version. Composite runs and batches fix the package version when they start, so publishing mid-run doesn't mix versions.
  • Validation versus run. Validation records the package version; when a run uses a different one, the run report and scenario page show "validated with #3, this run #5" and the differences (e.g. pandas 3.1.0 → 3.2.0), without blocking the run or re-validating automatically (D6).
  • Rollback. Old versions aren't deleted. The server keeps the files used by the latest 10 versions (configurable) and Workers keep the latest 3 environments, so going back one version needs almost no download.

Security

  • Who can change it. System administrators only; adding, removing, publishing, restoring and changing sources all go into the audit log (ADR 0025).
  • Wheels only, pinned by sha256. Installing never runs package code; Workers accept only files whose hash matches the list.
  • Cooldown. By default versions uploaded less than 7 days ago aren't chosen (uv's --exclude-newer), lowering the chance of installing a just-compromised release; explicitly asking for a newer version needs another confirmation.
  • Hashes checked separately. When resolving from a mirror, newly added files' sha256 are checked against pypi.org's JSON API (small requests); when it can't be reached the page says "hashes from this source only".
  • See before adding. Home page, license, first and current upload times; wheels containing a .pth file (code Python runs at startup) need an explicit confirmation.
  • Not allowed. Installers such as pip, setuptools and uv; playwright (runtime mode doesn't open browsers, ADR 0020); modules named like rpa_script, rpa_* or the standard library.
  • Still not a sandbox. Python nodes already run arbitrary code as the Worker's user (ADR 0020). Packages have the same trust level as scenario scripts and travel over the same authenticated Worker API.

Compatibility and upgrading

  • No full installer. All code is in the code layer (rpa_server, rpa_worker, rpa_runner) and upgrades with the update file (ADR 0018); the bundled runtime and the runtime IDs don't change; the server downloads uv itself.
  • Default behavior unchanged. #1 equals the bundled runtime; without package changes after upgrading, runs give the same results and Workers download nothing.
  • Older code layers. Devices report a new capability pythonPackages; when the current package version isn't #1, runtime-mode tasks go only to devices with it (devices follow the server's version, so they usually have it soon).
  • Not affected. The recorder (it has no runtime); compatibility-mode Python nodes (they still use the App's own Python).
  • The repository's runtimes/python/. Still the defaults for new installations and the source CI builds the bundled runtime from. When the bundled defaults change later, the page says "The App's default packages have new versions" and the administrator decides whether to apply them; nothing changes automatically.
  • Later. A new Python minor version (runtime 2) gets its own list per major version. ADR 0020's optional layer for model packages (D4) can use the same mechanism later (a second list dispatched only to Workers that chose it), designed then.

Phases and verification

  • Phase 1. Tables and migration, getting uv, resolving and platform checks, source speed tests and the downloader, the wheel store, the admin page (add, remove with affected scenarios, differences, check, publish, history, restore, settings), audit; the Worker API's list and files, building and preparing ahead on Workers, dispatch and reports; docs (this ADR, management Portal, Python nodes, remote Workers, in three languages).
  • Phase 2. Uploading wheels for offline servers, exporting and importing lock files (the same one on test and production servers), trying a version on chosen devices before publishing, looking up known vulnerabilities in OSV (D8).
  • Automated tests. A fake package source from a local wheel folder, no network; resolving, platform checks, source fallback and resuming, building, cleanup, dispatch, permissions and audit. CI's RPA Python runtime jobs build real package environments on each platform and run Python nodes in them.
  • Manual acceptance. Add tabulate and scikit-learn on the admin page, remove one, restore the previous version; run a Python node that uses them once on a Windows Worker and once on the Linux server; check download sizes and times.

Consequences

  • Adding a package goes from "change the repository, release, reinstall every device from the full installer" to "add a row on the admin page, publish, and Workers fetch it over the LAN". Small packages take seconds; ones like scikit-learn, tens of MB per platform, are still downloaded from the internet only once.
  • The server gains uv (about 20 MB) and a wheel store (from about 30–40 MB per platform in use, growing with packages). Each package environment on a Worker is a few hundred MB unpacked, and 3 are kept.
  • Servers can have different packages. Moving scenarios to another server means checking it has the packages they need (export and import in phase 2 address this).
  • Administrators can install any package on PyPI that has wheels; safety comes from system-administrator-only changes, the audit log, the cooldown and hashes, not technical isolation.
  • Python nodes run in the package environment's venv instead of the bundled interpreter, adding a path to CI's runtime tests; venvs on Windows must be verified for real in phase 1.
