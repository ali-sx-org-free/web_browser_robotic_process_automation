ADR 0021: Flow control inside scenarios is block steps in the DSL; the contract and the publishing gate stay the same

Conditions, loops and error handling are blocks among the steps (if, forEach, repeat, try), and conditions are written like expect; retries apply only to actions without side effects; step records follow the order steps ran and map to definitions by their path in the scenario file. Outputs are still published only after the independent checks pass.

Context

Scenario steps used to be a single list run straight from top to bottom, stopping at the first failure. Real systems have notices that pop up only sometimes, tables to process row by row, pages to turn until the last one, optional parts that may fail without stopping the work, and reports that take a while to finish. In the MVP these went to Python scripts (ADR 0010), which lose the DSL's validation, step-by-step debugging, step replays and readability in review.

M7 on the roadmap is flow features; iframes, tabs opened by a click and uploads were done early (M7a–M7c), and downloads came with Python nodes. The DSL documentation has always said that retries apply only to steps without side effects.

Decision

  • Block steps. if (condition, then, else), forEach (items, as, steps), repeat (times/while/until, with max required for conditions) and try (steps, catch). A block is a step too: it has an id and can have onError; timeouts and tabs go on the steps inside.
  • Conditions are written like expect. Element and page checks use the same fields as expect, plus expression (truthiness in the Jinja sandbox), wait (default 0: only look now) and not. A condition that does not hold is not a failure; an error while checking is, so a mistake never quietly takes the wrong branch.
  • Variables and facts. The loop variable is named by as, with loop for the innermost loop; catch has error. Scopes are checked during validation. Facts inside loops are overwritten each round; only append collects them into a list.
  • Error handling and retries. Any step can have onError: continue; retry is only for goto, waitFor, expect, extract and screenshot, so repeating a click or fill must be written out with if or try. A passed deadline and the record limit cannot be caught or continued.
  • The independent checks still decide the result. When failures continued or were caught, reports, replays and validation results show a reminder without blocking publishing.
  • Records follow the run and map by path. Top-level steps are listed from the start; steps inside blocks are inserted after their block when they run, with path, parent, iteration and similar fields. Replays, composite reports and step-by-step debugging all map to the scenario snapshot by path. Limits: 1,000 items or rounds per loop, 5 levels of nesting, 10,000 records per run.
  • Tabs you open yourself. openPage (as, url) and closePage (page), sharing names with M7b's popup.
  • Compatibility. All new fields are additions and schemaVersion stays 1; scenarios that use them carry the extension flow, so older recorders and Workers do not receive them.

Consequences

  • Common branches, row-by-row work, paging and optional steps stay in the DSL, still validated, debuggable and replayable; Python nodes remain the escape hatch.
  • Step records no longer match the scenario's steps one to one: readers must use path (older records without path map in order).
  • Step-by-step debugging must know which item a step inside a loop uses: the debug page lets you pick the current item, and error inside catch is a sample value.
  • Conditions and loops cannot be recorded and are written in YAML; the scenario editor has templates, and M5's AI can generate them later.
  • One run may have many records: step screenshots stay capped at 500, going over the record limit fails the run, and large amounts of data belong in batch runs (M7.3).

Alternatives not chosen

AlternativeWhy not
Write all flow in Python nodesLoses the DSL's validation, step-by-step debugging and step replays; runtime mode cannot open a browser (ADR 0020).
Expand steps before the run with Jinja if and forThe page is not open yet when expanding, so it cannot react to what is on screen; the expanded steps no longer match the scenario file.
A when field on each step instead of if blocksBranches of several steps would repeat the condition on each one; it can be added later as a shorthand for if.
Automatic retries for clicks tooSubmitting a form twice creates two records, against “retry only steps without side effects”.
Facts inside loops turn into lists automaticallySingle values would become lists too and invite mistakes; append makes collecting explicit.
Conditions, loops and parallel nodes in composite scenarios at the same timeThat is flow between nodes (a separate question left from the M6 prototype) and awaits its own decision.
