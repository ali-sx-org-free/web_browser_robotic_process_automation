ADR 0023: A sub-scenario is the DSL's call step, and its fixed revision is stored with the calling scenario's revision

A scenario uses call to carry on in the same browser and the same tab with a fixed revision of another scenario: the inputs are checked against the sub-scenario's contract, and its outputs come back only when its own independent checks pass. The scenario file of that revision is copied unchanged into the calling scenario's revision and counts toward its content hash, so the calling scenario runs on its own and what passed validation is what runs later.

Context

M7.1 lets a scenario branch and loop, but every scenario is still written from start to finish: the same stretch of work (“create a customer”, say) is written again in each scenario that needs it. Composite scenarios (M6) chain scenarios together, but every node opens its own browser and runs on its own, so they cannot carry on “on the same screen”, and they cannot be called once per item inside a loop.

The publish gate relies on the content hash to confirm that what passed validation is what gets published and run (ADR 0015). If sub-scenarios were looked up at run time, a new revision, archiving, or a sub-scenario not synced to that server would change the calling scenario's behaviour without a new revision of it; remote Workers and Recorders would also have to fetch sub-scenarios separately.

Decision

  • It is written as one step. action: call; scenario and revision name the fixed revision, inputs gives the inputs, as stores the outputs as a fact, and append: true collects the outputs of every call in a list. It can sit inside blocks, can have onError: continue and can be caught by try; it cannot retry or have timeout.
  • The contract is the sub-scenario's own. Inputs are checked against its contract before its first step; when its steps finish, its own verify runs straight away, and only then are outputs produced. If any part does not pass, the call step fails. The calling scenario's verify and the publish gate are unchanged.
  • One browser, separate namespaces. The sub-scenario carries on in the tab the call names, with the calling scenario's browser, login state and deadline; facts, loop variables, tab names and screenshot file names are kept apart, and tabs the sub-scenario left open are closed when it ends.
  • The sub-scenario file travels with the calling scenario's revision. The scenario file of that revision is copied unchanged to calls/<ID>/<revision>.yaml (those the sub-scenario calls itself sit flat in the same folder), is listed among the scenario's source files and counts toward the content hash. Scenarios that do not use call keep their hash.
  • The server brings it in when saving. A newly added call must point at a published revision (the same rule as composite scenario nodes: the scenario exists and is not archived, the revision exists, has no problem and was published). Sub-scenarios already brought in by the previous revision are not checked again: if a sub-scenario is archived later or this server no longer has it, the calling scenario can still be edited elsewhere and saved. calls/ files sent to the server are not taken as they are; when this server has that revision, its copy is always used.
  • The limits of the first version are checked by validation. The sub-scenario must be a DSL scenario; the login role is the same or it needs no login; its Secrets must be declared by the calling scenario; no file inputs or outputs; at most 3 levels and 10 different sub-scenario revisions; no looping back to itself.
  • Records map by path. The sub-scenario's step records follow the call; after "call", path is the position inside the sub-scenario. Replay and the report find the source text in calls/ of the run folder's snapshot.
  • The call extension. It is compared together with whatever the sub-scenarios use; Recorders and Workers that do not understand it are not given the scenario. schemaVersion stays 1.

Consequences

  • A calling scenario's revision is complete by itself: remote Workers, Recorders, rpa run, domain folders and git sync need nothing extra for sub-scenarios, and what a validation record proves includes the sub-scenarios.
  • A new revision of a sub-scenario does not apply by itself: every calling scenario has to change revision, save a new revision, and validate and publish again. This is deliberate (the same as pinning node revisions in composite scenarios); the cost is updating each calling scenario after a sub-scenario is fixed, and there is no list yet of which scenarios use a sub-scenario.
  • When several scenarios call the same sub-scenario, each calling scenario's revision holds its own copy of the file (text, usually a few KB).
  • The server only guarantees that the copy equals the source revision when it has that source revision; for domain folders synced from elsewhere, the calling scenario's own hash and validation records are what count, and rpa pack check does not compare against the source.
  • In step-by-step debugging a call runs the whole sub-scenario at once and counts as having side effects; continuing a recording (which replays the existing steps first) does not support scenarios that use call yet.
  • Sub-scenarios cannot have file inputs or outputs; flows that pass files should use composite scenarios for now.

Alternatives not chosen

AlternativeWhy not
Look the sub-scenario up on the server by ID and revision at run timeThe Worker protocol, Recorders, rpa run and git sync would all need extra handling; a published scenario could not run once its sub-scenario is gone; the hash would not include the sub-scenario, so the publish gate could not prove what actually runs.
No fixed revision: always use the sub-scenario's currently published revisionPublishing a new revision of a sub-scenario would change the behaviour of every scenario that calls it, with no new revision or validation record for them; the user decided on fixed revisions (D8).
Expand the sub-scenario's steps into the calling scenario when savingThe boundary of the sub-scenario's inputs, verify and outputs would be lost, step ids and fact names would clash, and the scenario file would no longer show which part is a sub-scenario.
Share facts and variables between the sub-scenario and the calling scenarioThe sub-scenario could no longer be validated and reused by itself: its behaviour would depend on which facts the calling scenario happens to have.
Turn the sub-scenario's outputs into a list automatically inside loopsInconsistent with the rule for extract (D3 of M7.1 chose an explicit append), and a single call would get a list too.
