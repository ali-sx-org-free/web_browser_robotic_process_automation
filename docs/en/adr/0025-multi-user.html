ADR 0025: Multi-user means local accounts, per-domain roles, encrypted secrets and a hash-chained audit log

The management portal always requires signing in. The first version has local accounts only, and the first system administrator can only be created on the server machine; permissions are per domain (administrator, editor, runner, viewer), plus system administrators; secrets are encrypted with AES-GCM and stay global, changed only by system administrators; every request that changes something goes into an append-only audit log. Switching production to PostgreSQL is not part of this.

Context

Up to M7 the management portal had no sign-in: by default it only listened on 127.0.0.1, and Recorders opened it through their own gateway with a device token. Once a team shares it, it has to know who is who, limit who can change or run which scenarios, keep secrets out of a plain-text file, and leave a record of who did what that cannot be altered.

Scenarios, roles and composite scenes already live in domains (M11's domain folders, which are also the unit of git sync), while projects only group composite scenes; so following domains is the natural boundary for permissions.

Decision

  • Signing in is always required. Pages and /api go through the sign-in gate (rpa_server.gate): pages without a session go to /login?next=…, and /api returns 401. Only static files, sign-in/sign-out/first-administrator setup, the language switch, the API description (rpa serve recognizes a running portal by openapi.json), and the Worker, Client and Agent APIs, which have their own tokens or keys, bypass it. Opening the portal through a Recorder also requires signing in (a Recorder's token only stands for the device).
  • Local accounts. Usernames use lowercase letters, digits and . _ -; passwords have at least 8 characters and are hashed with the standard library's scrypt (N=2^15, r=8, p=1). users.provider and subject are reserved for OIDC and LDAP. Accounts are disabled, never deleted (audit entries and memberships still point to them). The last active system administrator cannot be removed or disabled, and nobody can disable themselves.
  • The first system administrator can only be created on the server machine. While there are no accounts, /setup opened directly from 127.0.0.1 creates it (not through a Recorder or from another computer); servers without a browser use rpa user create USERNAME --admin. A forgotten password is reset with rpa user password USERNAME.
  • Sessions. After signing in the cookie holds a random token (HttpOnly, SameSite=Lax, Secure over HTTPS), named with the server ID; the database only stores its SHA-256. A session ends after 7 days without use and lasts at most 30 days; changing the password (other sessions end), resetting it and disabling the account end that account's sessions. After 5 failures for an account within 15 minutes signing in pauses; unknown accounts still cost one hash, so response times do not reveal whether an account exists. Write requests also keep the existing same-origin check (Origin).
  • Per-domain roles. domain_members: administrator (members, the domain's name and description, git sync), editor (create, change, validate and publish scenarios and composite scenes, record, step-by-step debugging, the domain's login roles), runner (run, batches, cancel, rerun), viewer (see scenarios, composite scenes, runs, batches and replays). System administrators can do everything without joining, and also handle accounts, creating and deleting domains, projects, secret values, devices, API clients, server settings and the audit log. Things without a domain (unassigned) are for system administrators only. Projects carry no permissions.
  • The gate checks path rules. A rule table (gate.RULES, first match wins) says which capability is needed and which kind of thing's domain to look at; runs, batches, composite runs and debugging sessions are each traced to their domain (a run follows its scenario, a composite batch its composite scene). Domains you cannot see give 404 (existence is not revealed); things you can see but not do give 403. Where the domain is only known from the request body (new scenario, new composite scene, new login role, moving to another domain), the route checks again. Unlisted GETs only need a signed-in user (lists are filtered separately); unlisted writes are for system administrators only (deny by default).
  • Lists are filtered by domain. The current user lives in a ContextVar (rpa_server.access); domains, scenarios, runs, composite scenes, composite runs, batches, login roles and the composite editor's scenario library only list domains you can see; background work has no user and is not restricted. Menus hide pages only system administrators can use; recording is shown to people who are an editor in at least one domain.
  • Encrypted secrets. Every value is encrypted with AES-256-GCM (cryptography) with a random nonce and the name as associated data (renaming breaks decryption). The key comes from the RPA_SECRETS_KEY environment variable, or else secrets.key in the data folder (created on first start, 0600). Old plain values become ciphertext at startup; with the wrong key the names are still listed but marked unreadable, and runs treat them as unset. Secrets stay global; only system administrators set or delete them, and nobody can read the plain values.
  • An append-only, hash-chained audit log. audit_events records sign-ins, failed sign-ins, sign-outs, creating the first system administrator, and every /api write request (account, method and path, result, source address, which Recorder it came through); request content is not recorded. Each entry's hash is the SHA-256 of the previous hash plus this entry; there is no way to change or delete entries, verification recomputes from the start, and changing or deleting any entry in the middle breaks the chain from there. The Agent API keeps its own audit.

Consequences

  • The first visit after the upgrade creates a system administrator; the person who did it is then a system administrator, and others need an account and domain membership before they see anything.
  • The server adds cryptography: the runtime (python/) changes, so this upgrade needs the full server bundle rather than an update file (ADR 0018); the user accepted this.
  • The key file must be backed up with the data folder; if it is lost, the secret names remain and the values must be set again.
  • When a composite scene uses scenarios from other domains, people editing it do not see those scenarios in the library (only domains they can see); running a composite scene only depends on its own domain.
  • Deleting only the last few audit entries does not show; preventing that needs the latest hash stored elsewhere, left for when it is needed.
  • Older tests use Settings.skip_login (set only in code; from_env never reads it) to act as a system administrator; sign-in and permissions have their own tests.
  • HTTP on the LAN is still plain text (including the cookie); HTTPS comes in M9.

Alternatives not chosen

OptionWhy not
Per-project permissions (the earlier design draft)Projects only group composite scenes; scenarios, roles and git sync are all per domain (D2).
OIDC/LDAP in the first versionThe user chose local accounts first (D1); the fields and the sign-in flow leave room for them.
A default administrator password set by the command line or an environment variable at upgradeDefault passwords tend to stay unchanged; instead it can only be created on the server machine (D4), with rpa user when there is no browser.
A permission check in every routeOver a hundred routes are easy to miss; one rule table denies unlisted writes by default and is tested rule by rule, with routes only adding the domain known from the request body.
Recording whole requests in the audit logThat would record passwords and secret values; only the method, path and result are kept.
The operating system's keychain for secretsServers are often Linux without a desktop and the bundle must be portable; a key file in the data folder or an environment variable instead (D3).
