ADR 0024: Data-driven runs are batch runs, and each row is one ordinary production run

Upload or paste a table; each row is a set of inputs, and each row runs a published scenario revision once in production, with its own report, outputs and replay. A batch keeps the table, the column mapping and the options, and its scheduling is worked out again from the database every time. When it ends you can export the results and rerun only the rows that did not pass (editing those rows' cells first if needed).

Context

A common need is “do the same flow once for every entry in a list”: create orders one by one, set up accounts one by one. The forEach of M7.1 handles items one after another inside a single run, but an error in one entry has to be caught with try, the result is a single report, and afterwards you cannot tell which screen belonged to which entry. Creating orders one by one usually needs evidence for every entry, and a way to redo only the few that failed.

Production runs already have contract checks, reports, outputs, replay, run locations and the Agent's limits; what is missing is turning a table into many production runs and seeing the result of every row.

Decision

  • A row is one ordinary production run. A batch fixes the scenario's published revision when it is created; each row queues one run with the purpose execution (runs.batch_id, batch_row), with the same report, outputs, replay and run location as a manual run. The Worker, the recorder and the executor know nothing about batches.
  • The table is stored as text. Paste it (tab- or comma-separated) or upload CSV, TSV or Excel (.xlsx, the first worksheet; dates become ISO text according to the cell format). The first row holds the headings; at most 1,000 rows, 50 columns and 5 MB, and 10,000 characters per cell. Cells are stored as text and only converted to inputs just before a row is queued.
  • Columns are mapped by heading, and the mapping can be changed. A heading maps to the input with the same name (or the same name once case, spaces, underscores and hyphens are ignored); inputs with no column, and empty cells, use their defaults. Conversion: numbers may have thousands separators; yes/no values accept true/false, 1/0, yes/no and 是/否; lists and objects are written as JSON; text with {{ }} is passed on unchanged to dynamic values; file inputs cannot come from the table. The converted values are then checked against the scenario contract, and a row with problems is marked “data problem” and not run.
  • Create first, then start. A new batch is “waiting to start”: you can change the column mapping and the options and see the check result of every row; once it starts they cannot change. Options: when a row does not pass, carry on or stop; how many rows to queue at once (1–10; how many actually run at once depends on how many Workers are free); browser, URL, headed/headless and run location as on the run form.
  • Scheduling is worked out from the database. Whenever a run ends (including one cancelled while queued), the batch is looked at again: which rows are running, which rows of this round have not been queued, whether a row did not pass; then it fills up to “rows at once” or ends. The same notice arriving twice, or a server restart, does not lose the thread; each row's idempotency key is “batch-row-attempt”, so a row is never queued twice. A row that cannot be queued (for example because the scenario was archived) records why and counts as not passed.
  • “Rounds” decide which rows run. Starting is round 1 and each rerun adds 1; only rows chosen for the current round are queued and counted as not passed. By default a rerun takes the rows that did not pass (failed, timed out, cancelled, needs login, could not be queued, data problem, never run); row numbers can be given instead; and the cells of those rows can be edited first (only existing columns; every run is still kept).
  • Stopping does not undo anything. A manual stop, or “stop when a row does not pass”, queues no more rows, and a manual stop cancels the rows that are queued or running; external actions that already happened are not rolled back.
  • The server produces the exports. CSV (UTF-8 with a BOM; values that start with =, +, - or @ and are not numbers get a leading ' so they are not taken as formulas) and Excel; the content is the original cells plus the status, the attempt, the run ID, every output and the error. The server reads and writes xlsx with the standard library instead of adding openpyxl.
  • The Agent API uses the same machinery. In POST /agent-api/v1/batches, each entry of rows is a set of inputs (input name → value), and the batch starts right away; if any row has a problem the batch is not created (422, listing each row's problems). Rows queued at once count toward the limit on queued and running runs; a client sees and stops only the batches it created.

Consequences

  • The evidence for every row is exactly that of a manual run, so the run list, replay and the Agent's run endpoints need no change; the cost is that 1,000 rows are 1,000 run records and run folders, kept under the ordinary retention rules.
  • A batch neither blocks publishing a newer revision of the scenario nor switches to it: to use the new revision, create a new batch.
  • Every row opens a browser and logs in once (with a login role, using the saved login state); for working through items on one screen in one browser, forEach is still the tool.
  • “Rows at once” only decides how many are queued; one Worker runs one row at a time, so real parallelism needs several Workers.
  • The server gains two tables (batches, batch_rows) and two columns on runs, which needs a database migration (0018).
  • Reading and writing xlsx ourselves covers the common cases (the first worksheet, shared strings, inline strings, number and date formats); a formula gives the result Excel saved, and a formula without a saved result reads as empty.
  • The first version covers published scenarios only; batches of composite scenarios (composites in projects), scheduled triggers and a limit shared between batches wait for actual need.

Alternatives not chosen

OptionWhy not
Only forEach: read the table as a list and work through it in one runAn error in one row affects the whole run, there is a single report, and the failed rows cannot be redone on their own; the user chose batch runs (D9).
Make a batch a new run purpose, or run the rows one by one on the WorkerReports, replay, run locations, the Agent's limits and the run list would all need separate handling, and the Worker protocol would change.
Convert every row to inputs when the batch is created and store themChanging the mapping or a cell would mean recomputing and storing two copies, and after a change to the conversion rules an old batch would no longer show its original data.
Judge a round by “runs created after it started”When rerunning chosen rows, rows that were neither chosen nor ever run cannot be told apart and get queued too; a row from an earlier round that could not be queued would make “stop when a row does not pass” stop at once.
Add openpyxl to the server to read and write ExcelThe distribution's Python dependencies change, so the runtime ID changes and an upgrade needs the full installer; all that is needed is reading the text of the first worksheet and writing one simple sheet.
Parse files and build exports in the browserThe Agent API needs the same checks and exports; the rules live once, on the server.
