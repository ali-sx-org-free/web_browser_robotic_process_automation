ADR 0026: Login roles and secrets are usable only when granted to an account or API client

A domain's four roles decide what someone can do with scenarios; login roles and secrets are granted separately, and only the granted accounts and API clients can see and use them. System administrators aren't restricted.

Context

A login role is an identity in a target system (for example "Test site: manager") plus the sign-in state the server keeps; whoever uses it acts as that identity in the target system. M8 only looked at the role in the scenario's domain: an editor in domain A could write login: { role: a role in domain B } and use domain B's saved sign-in. Secrets were the same: any editor could declare a secret in a scenario and type its value into a page they control.

Mainstream RPA platforms authorise "managing credentials" and "using credentials" separately in their credential vaults (for example UiPath's credential assets and Automation Anywhere's lockers); this follows the same idea.

Decision

  • Grants. credential_grants records which login role or secret is granted to which account (user:account id) or API client (client:ID). A domain's four roles are unchanged, and within a domain each role still includes the ones below it.
  • Who grants. Login roles are granted by the admins of their domain and by system administrators; global login roles and secrets by system administrators. Accounts can't claim them. Add or remove accounts and API clients under "Who can use" on each row of Logins & secrets.
  • Visibility. The list of login roles shows only the granted ones, plus those in domains you are an admin of (so you can choose who can use them); secrets show only the granted names. An API client's GET /roles and GET /secrets list only what it was granted.
  • Every use is checked. A scenario's login role and secrets: saving, publishing, validating, running, rerunning, batches (creating, starting, rerunning, each row queued), composite runs (starting, each node), step debugging and recording (a login role chosen, or continuing a recording). Sub-scenarios must use the same role and their secrets must be declared in the calling scenario (ADR 0023), so checking the calling scenario is enough. The login role itself: manual sign-in, sign-out and checking need the grant and at least runner in its domain; editing and deleting need the grant and editor; the person saving must have been granted the secrets its automatic sign-in uses. Signing in automatically with a login role doesn't need separate grants for the secrets it uses. Without permission the answer is 403 (login_role_forbidden, secret_forbidden), and the scenario page's "Before running" flags it first.
  • Background work uses who started it. Batches and composite runs record the account that started or reran them (user_id; API clients use the existing client_id), and each later row and node is checked against it: if the grant is removed or the account disabled midway, what hasn't started fails. Background work with nobody behind it (git sync, importing examples, converting recordings) isn't checked.
  • System administrators aren't restricted. They can see and use everything, recorded in the audit log as in ADR 0025.
  • A new login role is granted to whoever created it.
  • Upgrade. On the first start after upgrading, existing API clients are granted the login roles in the domains they may use (global ones included) and all secrets, with one audit entry, once only, so what ran before the upgrade still runs. Accounts aren't granted automatically.
  • Deleting. Deleting a login role, a secret or an API client deletes its grants too.

Consequences

  • After upgrading, only system administrators can use login roles and secrets until other accounts are granted them; this is expected (no release was made between merging M8 and this change).
  • Referring to a login role in another domain (ADR 0015's requires) still works: whether it can be used depends on the grant, decided by the admins of the login role's domain. The assessment had suggested "only login roles in the same domain or global ones"; while implementing, this turned out to break ADR 0015's existing cross-domain dependencies, and grants already close the original problem, so that restriction isn't added.
  • Anyone who can see a scenario still sees the login role ID and secret names written in its file (names only, no values or sign-in state).
  • Screenshots, recordings and replays of runs follow the domain permissions of ADR 0025, not grants.
