Multi-user and internal systems

What the two premises, shared team use and internal target systems, concretely require from the design.

Multi-user

Implemented in M8 (ADR 0025); single user before that
Authentication
Local accounts (passwords hashed with scrypt); the account table keeps provider and subject for OIDC and LDAP later (the company's AD or SSO). The management portal's pages and API always require signing in; the first system administrator can only be created on the server machine (/setup on 127.0.0.1, or rpa user create --admin). Device pairing, worker and Recorder tokens and Agent API keys are unchanged.
Permissions
Per domain: each domain's members are administrators, editors, runners or viewers, covering that domain's scenarios, composite scenes, runs, batches and replays. Domains you cannot see are left out of lists, and opening their URLs gives 404. Projects only group composite scenes and do not carry permissions.
Secrets
Stored encrypted with AES-256-GCM (the key is secrets.key in the data folder or the RPA_SECRETS_KEY environment variable, and must be backed up with the data). Secrets are global and only system administrators set or delete them; scenarios and login roles reference them by name, and nobody can read the plain value. They are sent only to the worker or Recorder that needs them.
Who can use login roles and secrets
M8.1 (ADR 0026): login roles and secrets are also granted to accounts and API clients, and only the granted ones can see and use them (saving, publishing, validating, running, batches, composite runs, step debugging, recording and manual sign-in are all checked). Admins of a login role's domain choose who can use it; system administrators do so for global login roles and secrets, and aren't restricted themselves.
Auditing
Sign-ins, sign-outs, failed sign-ins and every request that changes something (who, when, which path, the result) are appended and never changed, chained by hashes: changing or deleting any entry in the middle shows up when the chain is verified. System administrators see it under Admin › Audit log.
Versions
Every save of a scenario creates a new immutable version; each run points to its exact version. Revisions and validation and publishing records live in the domain folders and can be reviewed through git (M11).
Database
Production uses PostgreSQL, which supports several workers and concurrent writes; SQLite is only for development and prototypes (single machine, single process). See ADR 0008.
Stateless runner
From M2 on it only takes scenarios, inputs and secrets and outputs results and artifacts, so it moves into the M3 background worker, the M9a remote workers and the M10 Worker app unchanged.

There are also system administrators: they can do everything in every domain without joining, and handle accounts, creating and deleting domains, projects, secret values, devices and API clients, server settings (including the limit shared by batches) and the audit log. Schedules (scheduled runs) belong to M9, which decides who may set them.
