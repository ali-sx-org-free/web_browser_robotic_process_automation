多用户与内部系统

团队共用与内部系统这两个前提，对设计提出的具体要求。

多用户

M8 实现（ADR 0025）；之前是单用户
认证
本地账号（密码用 scrypt 哈希）；账号表预留 provider、subject 给之后的 OIDC 与 LDAP（公司的 AD 或 SSO）。管理 Portal 的页面与 API 一律要登录；第一个系统管理员只能在服务器那台电脑上（127.0.0.1 的 /setup，或 rpa user create --admin）创建。设备配对、Worker 与录制端的权杖、Agent API 的密钥照旧。
权限
以「领域」为单位：每个领域的成员是管理员、编辑者、运行者或查看者，管的是那个领域的场景、组合场景、运行、批量与回看。看不到的领域不出现在清单里，直接打开网址是 404。项目只是组合场景的分组，不管权限。
Secrets
AES-256-GCM 加密存放（密钥在数据目录的 secrets.key 或环境变量 RPA_SECRETS_KEY，要和数据一起备份）。Secrets 是全域的，只有系统管理员能设置与删除；场景与登录角色照名称引用，任何人都读不出明文。只送到需要它的 worker 或录制端。
审核
登录、注销、登录失败，以及每一个改变东西的请求（谁、何时、哪个路径、结果），只增不改，每一笔串成哈希链：改了或删了中间任何一笔，验证时就看得出来。系统管理员在「管理后台 › 审核记录」查看。
版本
场景每次保存产生不可变的新版本；运行记录指向确切版本。版本、验证与发布记录都在领域文件夹，可以经由 git 审阅（M11）。
数据库
正式环境用 PostgreSQL，支持多个 worker 与并发写入；SQLite 只用于开发与原型（单机、单一进程），见 ADR 0008。
Runner 无状态
从 M2 起只接收场景、入参与 Secrets，输出结果与产物；放进 M3 的背景 worker、M9a 的远程 worker 与 M10 的 Worker App 时都不用改。

内部系统带来的要求

情况对策落在
目标系统只能从内网访问平台与 worker 都部署在内网；worker 与录制端必须能直连目标系统，只有它们连服务器、服务器不连它们M9a、M10
每次运行都要登录每个角色保存并重用自己的登录状态（Playwright storage state），减少登录次数、降低账号锁定的风险；登录失效时回报 needs_login，引导人工重新登录后续跑M4
老系统缺少语意化标签定位器更依赖 css、xpath 与文字；录制器避开自动生成的 id，产出稳定的选择器M1、M4
iframe定位器以 frame 指定元素所在的 iframe（可嵌套），见 DSLM7a
点击开出的新分页（弹出窗口）开出新分页的步骤写 popup，在新分页上的步骤写 page，见 DSLM7b
自己开的新分页DSL 提供开新分页的步骤M7
文件上传（导入 Excel、上传图片）入参的 type: file 与 upload 步骤；文件在运行时上传或用场景附件，见 DSLM7c
文件下载download 动作；下载文件作为产物保存M7
表格数据抽取extract 支持表格转成结构化数据M1
自签凭证场景层级可设置忽略 HTTPS 错误，默认关闭并在审核时标示M2
页面内容可能敏感AI 生成可切换到自建模型；截图、录像与回看依领域的权限访问M5、M8
录制、调试与人工登录的浏览器开在录制者自己的电脑：M4 时是运行平台的那台，M10.2 起是通过录制端 App 操作时的那台录制端，服务器可以没有屏幕。远程浏览器画面实时传输不做（ADR 0014）。测试网站（M2）先沿用 MVP 原型的本机测试页，之后扩充成典型内部系统：登录、菜单、iframe（M7a 的 /frames）、表格与文件下载。
