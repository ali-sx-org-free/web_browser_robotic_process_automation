ADR 0027：RPA Python 运行环境的包由服务器管理，Worker 从服务器取得

系统管理员在管理后台添加、移除 Python 节点能用的包；服务器解析出一份锁定档、从最快的来源下载一次 wheel，Worker 从区网取得缺的文件，用 App 内附的解释器组成同一个包环境。不用重装任何 App。

影响范围
rpa-server（数据表与迁移、包管理页、解析与下载、Worker API）、rpa-worker（回报、下载、预先准备）、rpa-runner（包环境的组装与运行，pyruntime.py）、文档。rpa-core 的 DSL、录制端、兼容模式的 Python 节点不改；内附的运行环境压缩档与 runtimes/python/ 不改。
相关
ADR 0020（Python 节点与 RPA Python 运行环境）、ADR 0018（分层更新、环境代号）、ADR 0012（远程 Worker）、ADR 0025（系统管理员、审核记录）。

背景

RPA Python 运行环境 1.0.0 是 Python 3.13.14 加上 9 个包（连依赖 18 个：openpyxl、xlsxwriter、xlrd、pandas、python-dateutil、python-docx、pypdf、charset-normalizer、requests）。清单在仓库的 runtimes/python/requirements.in，CI 为四个平台建置、自我测试，附在 Worker App 与 Linux 服务器分发包；Worker 上拿掉了 pip、放了 EXTERNALLY-MANAGED，不能另外安装。

要多一个包，现在只能改仓库、升运行环境的次版本、发新版。压缩档的文件名算进环境代号（ADR 0018），所以每台 Worker 与服务器都要用完整的安装包重装。

下载速度是实际的问题。公司的网络连 PyPI 慢：2026-10-20 服务器的 uv sync 太慢而加了镜像测速（scripts/setup-linux.sh）；2026-10-21 浏览器下载实测官方来源约 0.8～1.7 MiB/s、国内镜像约 5 MiB/s。现在的默认包每个平台的 wheel 合计约 30～36 MB（2026-11-27 查 PyPI：Windows 约 30、macOS 约 34、Linux x64 约 36 MB）；加 scikit-learn 每个平台多约 23～45 MB（numpy 已经有）。

目标

  • 系统管理员在管理后台添加、移除包，发布后所有 Worker 自动用新的包。
  • 默认就是现在的 9 个包，和内附的运行环境完全相同；不改的话行为与下载量都不变。
  • 添加包快：互联网只下载一次、从最快的来源、只下载多出来的；Worker 从区网取得、在空闲时预先准备。
  • 每台 Worker 的包与版本相同，可以回到之前的版本。
  • Worker 不连互联网；不用重装任何 App 或分发包。

  │  Worker API：这一版、这个平台的清单与文件（区网、可续传、同时最多 4 台）
  ▼
Worker：内附运行环境（解释器＋默认包）＋ 缺的 wheel ─▶ 包环境 venv（#N）─▶ Python 节点
  • 解释器与包分开。App 与分发包内附的 RPA-Python-1.0.0-<平台>.tar.gz 照旧，第一次照旧解压到缓存；但它只当成解释器与默认包的来源。Python 节点实际在「包环境」运行：用内附的解释器创建的标准 venv（不含 pip、不看内附的 site-packages），里面只有这个包版本列的包。脚本用 sys.executable 开的子进程也在同一个环境。
  • 包清单在服务器。每个运行环境主版本一份（目前只有 1），存在服务器的数据库，所有 Worker 共用（D1）。第一次启动时用程序内附的默认清单与锁定档创建「包 #1」，和内附的运行环境相同。添加、移除先改草稿，检查通过后发布成 #2、#3……；发布的版本不再改变。
  • 解析在服务器做一次。uv pip compile --universal --only-binary :all: --python-version 3.13 输出 PEP 751 的 pylock.toml：每个包的确切版本，每个 wheel 的网址、大小、上架时间与 sha256。以上一版的锁定档为起点，添加包时其他包的版本不变（2026-11-27 用 uv 0.11.32 实测：加 tabulate 后 numpy、pandas、xlsxwriter 维持锁定的版本）；按「检查更新」才升级。uv 由服务器第一次用到时从包来源下载固定的版本（版本与 sha256 写在程序里，D7）。
  • 只收 wheel，每个平台都要有。不收源代码包：服务器与 Worker 都不编译、不运行安装程序。服务器依四个平台（windows-x86_64、macos-arm64、linux-x86_64 glibc 2.28、linux-aarch64）的条件逐一确认每个包有能用的 wheel；缺的时候说明缺哪个平台，可以改成「只在这些平台安装」（加上平台条件，例如 pywin32 只在 Windows），用到它的场景要写 platforms，校验时提醒（2026-11-27 实测：没有条件的 pywin32 会被锁进所有平台，所以要另外确认）。
  • 文件集中在服务器。wheel 依 sha256 存在服务器数据目录的 python-packages/，各版本共用；Worker 只向服务器取（Worker API），不连互联网。
  • 派工与报告。任务带着包版本；同样能运行的 Worker 中，已经准备好这一版的优先。还没准备好的在运行的「运行环境」阶段准备（照 ADR 0020 不算进总期限）。result.json 的 python 多 packages：包版本、锁定档哈希、沿用或这次准备、下载了多少。

下载速度

做法效果
互联网只下载一次服务器是唯一对外下载的地方，每个文件（以 sha256 认）只下载一次，所有 Worker 从区网取。50 台 Worker 加一个 40 MB 的包，外网只下载「40 MB × 用到的平台数」，不是 2 GB。
选最快的来源包来源默认「自动」：PyPI、清华、中科大、阿里云、腾讯云、华为云（和 scripts/setup-linux.sh 相同）各下载同一个已知 sha256 的文件，内容相符而且最快的优先，其他依速度排成备援；结果显示在页面，24 小时内沿用。也可以指定其中一个、公司的 Nexus／Artifactory／devpi 网址，或设置 HTTP 代理与公司的根凭证（D3）。
换来源不影响内容锁定档记的是 sha256。用镜像时把文件网址的 files.pythonhosted.org 换成镜像的同一路径；下载后核对，不符就丢掉、换下一个来源，最后才用原始网址。
只下载用得到的平台服务器只下载「有设备的平台」（服务器自己与已配对 Worker 回报的平台）；新平台的设备第一次上线时才补。
只下载多出来的添加一个包只下载它和新的依赖，版本没变的不重新下载。内附运行环境里同名同版的包，Worker 直接从内附的运行环境拷贝：默认的 #1 在 Worker 上不用下载任何文件；加 scikit-learn 时 numpy 不用再下载。
并行与续传服务器同时下载 4 个文件（可调）；大档中断后用 HTTP Range 从断点续传；页面显示每个文件的进度、速度与来源。Worker 从服务器下载也能续传。
发布后预先准备闲置的 Worker 收到新版本后在背景下载、组装，不占任务时间；服务器限制同时下载的 Worker 数（默认 4 台，可调），不会一起塞满服务器的网络。
大包先提醒加入前显示每个平台要下载的大小，以及用目前来源的速度估计的时间；单一包超过 100 MB（例如 PyTorch）要再确认，并说明每台 Worker 的磁盘会多用多少。

管理后台「Python 包」

新的页面放在管理后台，只有系统管理员看得到（和用户、审核记录相同）。

  • 目前的包。直接加的包：名称、要求的版本、实际版本、平台、每个平台的大小、授权、简介、谁在什么时候加的；默认的标「默认」。依赖收合显示，标出被谁需要。
  • 添加。输入名称（怎么找到名称见找到需要的包），可以加版本条件（例如 tabulate、pandas>=3,<4），可以限定平台。先显示最新版本、简介、授权、首页、上架时间、四个平台有没有 wheel 与大小，再加进草稿。
  • 移除。从草稿拿掉；不再被需要的依赖一起拿掉，还被其他包需要的留着并说明。用 ast 扫描所有领域运行环境模式的场景（已发布与草稿）的 .py 档，列出 import 了这个包的场景；有已发布的场景用到时默认不能移除，写了原因才能强制移除（D2）。
  • 检查。解析、平台确认、下载（显示进度）、在服务器自己的平台组装并 import 每个直接加的包；列出和目前版本的差异（添加、移除、改版本，含依赖）与每个平台的下载量。
  • 发布、历史、回到某一版。回到某一版是用那一版的锁定档发布一个新版本，文件都还在，所以很快。
  • 设备的准备状态。每台 Worker 对目前版本是「已准备」「下载中 N%」「失败（原因）」或「App 太旧」；集群管理的设备页也显示。
  • 设置。包来源与测速结果、代理、冷却天数（D4）、Worker 同时下载的台数、保留几个版本。

Worker 上的包环境

<缓存>/python/
  1.0.0-windows-x86_64/   内附的运行环境
  wheels/<sha256>.whl     下载的 wheel
  envs/<哈希>-<平台>/     包环境（venv）

内附的运行环境照旧解压（解释器＋默认包）；wheels/ 是从服务器下载的 wheel，依内容命名、各版本共用；envs/ 是每个包版本的标准 venv，以锁定档的哈希命名，.ready 记同一个哈希。

  1. 向服务器取这一版、这个平台的清单：包、版本、wheel 文件名、sha256、大小。
  2. 内附运行环境里同名同版的包，依 dist-info 的 RECORD 拷贝（同一个磁盘用硬链接）；其他从服务器下载到 wheels/ 并核对 sha256。
  3. 用内附的解释器以标准函数库的 venv 创建环境（不装 pip、不含内附的 site-packages）。Windows 用 python-build-standalone 附的 venvlauncher.exe（2026-11-27 确认 3.13.14 的 Windows 版有）。
  4. 用标准函数库解开 wheel（照 wheel 格式放 purelib、platlib、data，不产生命令行程序），用 compileall 编译，再用新的环境 import 每个直接加的包。
  5. 写 .ready、改名成正式的文件夹。同一版同时只有一个进程在做（沿用现有的锁文件）；失败就丢掉，下次重来。

保留最近 3 版与正在用的环境，其他删除；wheels/ 里不再被保留的版本用到的文件一起删。Runner 用 envs/… 的解释器运行，参数照旧（-E -s -B -X utf8）。

找到需要的包

PyPI 没有给程序用的搜索（2020 年起关闭；2026-11-27 确认 XML-RPC 的 search 仍回错误，要人到网站搜索），镜像也没有。所以页面不做关键字搜索，而是从下面几个方向找到名称，最后都用「名称查询」确认能不能加。

  • 名称查询。输入包名称（不分大小写，-、_、. 视为相同）。服务器向目前的包来源取版本清单与每个文件的平台、大小、上架时间（PEP 691 的 simple API，镜像也有），再取该版 wheel 的 METADATA（PEP 658 的小文件）显示简介、授权、首页与依赖，都是小请求。结果列出最新版本与冷却期内可选的版本、四个平台各有没有 wheel 与大小，并先试解析一次，说明和目前的包会不会冲突、会多出哪些依赖。
  • 用 import 名称找。很多包的名称和 import 不同：import docx 是 python-docx、cv2 是 opencv-python-headless、yaml 是 PyYAML、PIL 是 pillow、fitz 是 PyMuPDF。输入的名称先比较程序内置的对照表与目前包的 top_level 名称，找不到才当成包名称查。
  • 常用包清单。程序内置一份依 RPA 用途分类的建议清单：Excel 与 Office 文档、PDF、图片与条码、数据库、文件传输与邮件、压缩、中文处理、Windows 自动化。每项附一句用途、授权与限制（例如 xlwings 要装 Excel、pywin32 只有 Windows、PyMuPDF 是 AGPL）；点一下带到名称查询。清单跟着代码层的更新档更新。
  • 从场景找缺的。用和移除时同一个 ast 扫描，列出运行环境模式的场景 import 了、但目前的包没有的模块（不算标准函数库、rpa_script 与场景 files 里自己的模块），每个附建议的包与「加进草稿」。
  • 运行时缺模块。Python 节点因 ModuleNotFoundError 失败时，运行报告说明「目前的包没有 X」并附建议的包；系统管理员看到 Python 包页的链接，其他人看到「请系统管理员加入」。
  • 到 PyPI 网站搜索。页面附链接，在浏览器打开 pypi.org 的搜索，用关键字找到名称后回来查询。

版本与一致性

  • 一个包版本是一份锁定档。确切版本加每个文件的 sha256；所有 Worker 组出来的包与版本相同，只有平台的二进位档不同。画面显示服务器内递增的「包 #N」，跨服务器比较用锁定档的哈希。
  • 场景文件不变。照旧写 runtime: "1"，不写包版本。
  • 一次运行用同一版。组合运行与批量在开始时固定包版本，中途发布新版也不会混用。
  • 验证时与运行时。验证记录记下包版本；运行时的版本不同时，运行报告与场景页显示「验证时 #3、这次 #5」和差异（例如 pandas 3.1.0 → 3.2.0），不挡运行、不自动重新验证（D6）。
  • 回退。历史版本不删。服务器保留最近 10 个版本用到的文件（可调），Worker 保留最近 3 版的环境，回到前一版几乎不用下载。

安全

  • 谁能改。只有系统管理员；添加、移除、发布、回退、改来源都记进审核记录（ADR 0025）。
  • 只收 wheel、锁定 sha256。安装时不运行包的程序；Worker 只接受清单里哈希相符的文件。
  • 冷却期。默认不选上架未满 7 天的版本（uv 的 --exclude-newer），降低装到刚被入侵的版本的机会；明确指定较新的版本时要再确认。
  • 哈希另外核对。从镜像解析时，新加入的文件另外向 pypi.org 的 JSON API 核对 sha256（都是小请求）；连不上时标示「只用某来源的哈希」。
  • 加入前看清楚。显示项目首页、授权、第一次与这一版的上架时间；wheel 里有 .pth（Python 启动时会运行的文件）的要特别确认。
  • 不能加。pip、setuptools、uv 之类的安装工具；playwright（运行环境模式不开浏览器，ADR 0020）；和 rpa_script、rpa_* 或标准函数库同名的模块。
  • 仍然不是沙箱。Python 节点本来就以 Worker 那位用户的身分运行任意程序（ADR 0020）。包和场景的脚本是同一个信任等级，经同一个已认证的 Worker API 发送。

兼容与升级

  • 不用完整的安装包。程序都在代码层（rpa_server、rpa_worker、rpa_runner），用更新档（ADR 0018）升级；内附的运行环境不变，环境代号不变；uv 由服务器自己下载。
  • 默认行为不变。#1 和内附的运行环境相同；升级后不改包的话，运行结果一样，Worker 也不用下载。
  • 旧的代码层。设备回报新的能力 pythonPackages；目前的包版本不是 #1 时，运行环境模式的任务只交给有这个能力的设备（设备跟着服务器更新，一般很快就有）。
  • 不受影响。录制端（没有运行环境）；兼容模式的 Python 节点（照旧用 App 内附的 Python）。
  • 仓库的 runtimes/python/。照旧是新安装的默认与 CI 建置内附运行环境的来源。之后内附的默认包改版时，管理页提示「App 内附的默认包有新版本」，由管理员决定要不要应用，不自动改。
  • 之后。换 Python 的次版本（运行环境 2）时每个主版本各一份清单。ADR 0020 的模型包选用层（D4）之后可以用同一套机制（第二份清单、只派给选了它的 Worker），那时再设计。

分期与验证

  • 第一期。数据表与迁移、uv 的取得、解析与平台确认、来源测速与下载器、wheel 库、管理页（添加、移除与受影响的场景、差异、检查、发布、历史、回退、设置）、找包（名称查询、import 名称、常用清单、从场景找缺的、缺模块的提示）、审核；Worker API 的清单与文件、Worker 的组装与预先准备、派工与报告；文档（本 ADR、管理 Portal、Python 节点、远程 Worker，三种语言）。
  • 第二期。脱机环境上传 wheel、导出与导入锁定档（测试与正式服务器用同一份）、发布前先在指定的设备试用、查询 OSV 的已知漏洞（D8）。
  • 自动测试。假的包来源用本机的 wheel 文件夹，不连网；解析、平台确认、换来源与续传、组装、清理、派工、权限与审核。CI 的 RPA Python 运行环境工作在各平台实际创建包环境并运行 Python 节点。
  • 人工验收。在管理页添加 tabulate 与 scikit-learn、移除一个、回到前一版；Windows Worker 与 Linux 服务器各运行一次用到它们的 Python 节点；看下载量与时间。

D4冷却期7 天。0（不限）或其他天数。
D5发布前要通过哪些检查服务器的检查（解析、平台、下载、在服务器的平台 import）一定要通过；其他平台在 Worker 准备时检查，失败时页面提醒并可以马上回退。每个平台都要有在线的设备检查通过才能发布；没有那个平台的设备时发布不了。
D6验证后包版本变了只显示差异，不挡运行，不自动重新验证。包改变后，受影响的场景要重新验证才能运行。
D7服务器的 uv 从哪里来第一次用到时从包来源下载固定的版本，不用重装服务器。放进服务器分发包：下次要用完整的分发包装一次。
D8分期先做第一期；第二期之后再排。两期一起做。
D9场景的编辑者能不能看到包、申请加入暂不做 用户 2026-11-27 04:00 America/Los_Angeles（PST，UTC−08:00）决定。这一版只有系统管理员看得到、加得了包，需求在平台外沟通；之后要做时再提出。原本的建议：第一期就做唯读的包清单与申请，由系统管理员处理。

后果

  • 加包从「改仓库、发新版、每台用完整的安装包重装」变成「管理页加一笔、发布，Worker 自动从区网取得」。小包几秒；scikit-learn 这样每个平台几十 MB 的，也只从外网下载一次。
  • 服务器多一个 uv（约 20 MB）与 wheel 库（每个用到的平台约 30～40 MB 起，依包增加）。Worker 每个包环境解开后数百 MB，保留 3 版。
  • 每台服务器的包可以不同。场景搬到另一台服务器时，要确认那台有需要的包（第二期的导出与导入解决）。
  • 管理员可以装 PyPI 上任何有 wheel 的包；安全靠只有系统管理员能改、审核、冷却期与哈希，不是技术上的隔离。
  • Python 节点的运行从「内附的解释器」改成「包环境的 venv」，CI 的运行环境测试多一条路径；Windows 的 venv 要在第一期实际验证。

没有选的方案

方案没有选的原因
照旧在仓库改清单、CI 建置、发新版每次都要完整的安装包，也不能在管理后台改；这次就是要改掉这点。
服务器每个版本重新打包整个运行环境（解释器＋包）再分发每次都下载整包 60～75 MB；服务器只能测自己的平台；解释器跟着重复下载。
Worker 直接从 PyPI 或镜像安装每台都要连得到外网、各自下载，时间与结果因台而异；Worker 上要有 pip 或 uv。
在内附的 site-packages 上叠一个文件夹（加进 sys.path）拿不掉默认包，同一个包会有两个版本并存；脚本开的子进程看不到叠上去的包。
每个场景自己声明、锁定包每台 Worker 要很多套环境，正是 ADR 0020 要避免的版本与依赖问题。
收源代码包（sdist）要在服务器或 Worker 上编译、运行安装程序，每个平台要有编译器；不安全也不能重现。
Conda另一套生态系、下载量更大，和现在的 python-build-standalone 不兼容。
