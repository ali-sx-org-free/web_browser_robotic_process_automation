ADR 0021：场景内的流程控制是 DSL 的区块步骤，契约与发布门槛不变

条件、循环与错误处理写成步骤里的区块（if、forEach、repeat、try），条件沿用 expect 的写法；重试只用于没有副作用的动作；步骤记录依运行顺序、以场景文件的路径对应定义。出参仍只在独立断言通过后发布。

背景

场景的步骤原本是一层清单，从头到尾直线运行，某一步失败就停。真实系统常有「有时跳出的公告」「一张表逐列处理」「翻页直到最后一页」「选填的部分失败也要继续」「报表要等一下才完成」。MVP 时这些交给 Python 脚本（ADR 0010），但脚本失去 DSL 的校验、逐步调试、步骤回看与审阅的可读性。

路线图的 M7 是流程能力；iframe、点击开出的新分页、上传已提前做完（M7a～M7c），下载由 Python 节点补上。DSL 文档一直写着「重试只用于没有副作用的步骤」。

决策

  • 区块步骤。if（condition、then、else）、forEach（items、as、steps）、repeat（times／while／until，条件模式必填 max）、try（steps、catch）。区块也是步骤：有 id，可以 onError；超时、分页写在里面的步骤。
  • 条件沿用 expect。元素、页面的检查字段与 expect 相同，加上 expression（Jinja 沙箱的真值）、wait（默认 0，只看当下）、not。不成立不算失败；判断本身出错算失败，不默默走错分支。
  • 变量与事实。循环变量以 as 命名，另有最内层的 loop；catch 里有 error。范围在校验时检查。循环里的事实每轮覆盖，append 才累积成清单。
  • 错误处理与重试。任何步骤可写 onError: continue；retry 只用于 goto、waitFor、expect、extract、screenshot，点击、填写等有副作用的动作要重复就明确写成 if 或 try。总期限、记录上限不能被接住或继续。
  • 结果仍由独立断言决定。有失败后继续或被接住的失败时，报告、回看、验证结果显示提醒，不挡发布。
  • 记录依运行顺序、以路径对应。最外层的步骤一开始列出，区块里的步骤运行到才插在区块后面，多了 path、parent、iteration 等字段；回看、汇总报告、逐步调试都以 path 对应场景快照。上限：每个循环 1,000 项／轮、嵌套 5 层、每次 10,000 笔记录。
  • 自己开的分页。openPage（as、url）、closePage（page），和 M7b 的 popup 共用名称。
  • 兼容。新字段都是增加的，schemaVersion 维持 1；用到的场景标上扩充 flow，旧的录制端与 Worker 不会领到。

后果

  • 常见的分支、逐列处理、翻页与选填步骤可以留在 DSL，照样校验、调试、回看；Python 节点仍是逃生门。
  • 步骤记录不再和场景文件的步骤一对一：读记录的地方要用 path（没有 path 的旧记录依顺序对应）。
  • 逐步调试要处理「循环里的一步用哪一项」：调试页可以选目前项，catch 里的 error 是示范值。
  • 条件与循环录不出来，要在 YAML 里写；场景编辑页有模板，之后 M5 的 AI 可以产生。
  • 一次运行可能有很多笔记录：步骤截图仍最多 500 张，记录超过上限算失败，大量数据改用批量运行（M7.3）。

没有选的方案

方案为什么不选
流程都写在 Python 节点失去 DSL 的校验、逐步调试与步骤回看；运行环境模式不能开浏览器（ADR 0020）。
用 Jinja 的 if、for 在运行前展开步骤展开时页面还没打开，判断不了画面上有什么；展开后的步骤和场景文件对不上。
每一步加 when 取代 if 区块多步的分支要每步重写条件；之后常用可以另加成 if 的简写。
点击也可以自动重试送出表单重复会重复建单，违反「只重试没有副作用的步骤」。
循环里的事实自动变成清单单值也变清单、容易误用；用 append 明确表示要累积。
组合场景层级的条件、循环、平行一起做那是节点之间的流程（M6 原型留下的另一组问题），另等决定。
