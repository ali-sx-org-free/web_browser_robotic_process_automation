ADR 0026：登录角色与 Secrets 绑定到账号与 API 用户端才能用

领域的四种角色决定能对场景做什么；登录角色与 Secrets 另外要绑定，绑定的账号与 API 用户端才看得到、用得到。系统管理员不受限制。

背景

登录角色是目标系统里的一个身分（例如「测试网站：主管」），加上服务器保存的登录状态；用它的人就是以那个身分操作目标系统。M8 只看场景所在领域的角色：甲领域的编辑者在场景写 login: { role: 乙领域的角色 }，就能用乙领域保存的登录状态。Secrets 也一样：任何编辑者都能在场景声明一个 Secret，再把值填到自己控制的网页。

主流 RPA 平台的凭证保管库把「管理凭证」和「使用凭证」分开授权（例如 UiPath 的凭证资产、Automation Anywhere 的 Locker），这里照同样的想法。

决策

  • 绑定。credential_grants 记哪个登录角色或 Secret 绑定给哪个账号（user:账号 id）或 API 用户端（client:代号）。领域的四种角色不变；同一个领域里的角色仍是一层包一层。
  • 谁指定。登录角色由所在领域的管理员与系统管理员指定；全域的登录角色与 Secrets 由系统管理员。账号不能自己认领。在「登录与凭证」每一列的「谁能用」加上或移除账号、API 用户端。
  • 看得到。登录角色的清单只列绑定的，加上自己是管理员的领域里的（才能指定谁能用）；Secrets 只列绑定的名称。API 用户端的 GET /roles、GET /secrets 也只列绑定的。
  • 用到的地方都检查。场景的登录角色与 Secrets：保存、发布、验证、运行、重跑、批量（创建、开始、重跑、每排一列）、组合运行（开始、每个节点）、逐步调试、录制（选了登录角色或接著录制）。子场景必须用同一个角色、Secrets 也要声明在调用的场景（ADR 0023），所以看调用的场景就够。登录角色本身：人工登录、注销、检查要已绑定而且在那个领域至少是运行者；修改、删除要已绑定而且是编辑者；自动登录用到的 Secrets，保存的人要已绑定。用登录角色自动登录时不必另外绑定它用到的 Secrets。没有权限时 403（login_role_forbidden、secret_forbidden），场景页的「运行前要准备」先标出来。
  • 背景排的看开始的人。批量与组合运行记下开始或重跑的账号（user_id；API 用户端用原有的 client_id），之后排的每一列、每个节点用他检查：中途取消绑定或禁用账号，还没开始的就失败。没有人的背景工作（git 同步、导入示例、录制转换）不检查。
  • 系统管理员不受限制。能看能用全部，照 ADR 0025 留审核记录。
  • 新建的登录角色绑定给创建的人。
  • 升级。升级后第一次启动，把既有的 API 用户端绑到它可用领域里的登录角色（全域的也算）与所有 Secrets，审核记录记一笔，只做一次；让升级前能跑的照样能跑。账号不自动绑定。
  • 删除。删除登录角色、Secret、API 用户端时一并删除绑定。

后果

  • 升级后只有系统管理员能用登录角色与 Secrets，直到指定其他账号；这是预期的（M8 合并到这次之间没有发布版）。
  • 跨领域引用登录角色（ADR 0015 的 requires）照样可以：能不能用看绑定，由登录角色所在领域的管理员决定。评估时建议过「只能用同一个领域或全域的登录角色」，实现时发现会打破 ADR 0015 已有的跨领域依赖，而绑定已经挡住原本的问题，所以不加这条限制。
  • 看得到场景的人仍看得到场景文件里写的登录角色代号与 Secret 名称（只是名称，没有值与登录状态）。
  • 运行的截图、录像与回看照 ADR 0025 依领域的权限，不另外看绑定。
  • 绑定只管存在 Portal 的 Secrets。场景声明了、但 Portal 没有存的名称，值由运行那台电脑的环境变量提供（M2 起的做法），那是那台电脑的管理者给的，不必绑定；两边都没有值时照旧停在入参阶段。要管住就把它存进 Portal。

没有选的方案

方案没有选的原因
只靠领域的角色就是这次要补的问题：登录角色与 Secrets 跨出它们所在的领域。
只绑定登录角色，Secrets 不管编辑者仍能在场景直接引用 Secret、把值填到别的网页。
只在运行时检查没绑定的编辑者照样能写步骤，再让绑定的人去跑；所以保存与调试也检查。
账号自己认领、管理员核准多一道流程；第一版由管理员直接指定，之后需要再加。
群组目前人数不多，直接绑定账号；群组之后再做。
