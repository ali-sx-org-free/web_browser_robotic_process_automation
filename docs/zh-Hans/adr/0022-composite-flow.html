ADR 0022：组合场景的条件写在连接上、同时运行分给不同的 worker、重复是固定次数

组合场景（DAG）节点之间的流程：连接看来源节点的出参决定走不走，没走到的节点略过；同时就绪的节点可以一起排入队列，由空着的 worker 各自领取；节点可以固定重复几次，下游用最后一次的出参。调度每次都从节点的结果重新算，不另外存略过与次数。

背景

M6 的组合场景是 DAG：可分叉、可汇合，依拓扑顺序一个接一个运行，失败即停。MVP 原型另外展示了平行节点、条件分支与重复次数，当时刻意不做，列在未完成工作。场景内的条件与循环已由 M7.1 做成 DSL 的区块（ADR 0021），节点之间的流程是另一组问题：判断的依据是上游节点发布的出参，而不是页面。

一次组合场景运行的节点原本都交给第一个节点领取的 worker，而且每台 worker 一次只跑一个浏览器，所以同时就绪也只能逐个运行。

决策

  • 条件写在连接上。连接多 when（看来源节点的一个出参：equals、notEquals、in、empty）或 otherwise（来源的其他条件连接都不成立）。节点的上游都结束后，有一条连接走到就运行，一条都没有就略过，略过往下传。出参绑定也算一条无条件的连接；同一对节点有画出的连接时依那条连接的条件。
  • 同时运行分给不同的 worker。定义的 concurrency（1～10，默认 1）是同时就绪的节点最多几个一起排入队列。大于 1 时节点不再固定给第一台 worker；指定了 worker、从失败的节点继续、或用到上游文件出参时才固定。Worker 与桌面 App 不改，一台 worker 仍一次跑一个浏览器。
  • 重复是固定次数。节点的 repeat（1～20）一次接一次跑，每次都是一个运行、都要通过；下游用最后一次的出参。从失败的节点继续时，重复到一半的节点从没通过的那一次接着跑。
  • 调度从结果算。rpa_core.workflow.advance 从每个节点的状态与出参算出可以开始的、略过的与是否结束；服务器每次通知都重新算，重复通知不会排两次，重启时照样能接着走。
  • 失败即停照旧。有节点没通过就不再排新的节点；同时在跑的节点跑完才停下。条件略过不算失败；发布门槛不比较没有跑的略过节点。
  • 只有第 2 版。三个字段只能用在第 2 版（DAG）；没用到的定义 JSON 与哈希不变。

后果

  • 要真的同时跑，需要多台 worker（同一台电脑开两个 rpa worker 也算两台）。只有一台时行为和以前一样。
  • 分到不同 worker 的节点不共用工作文件夹；靠文件出参交接的节点会留在同一台，其他方式共用的文件不保证拿得到。
  • 回看照节点顺序接起来，同时跑的节点不是多轨同时播；重复的节点播最后一次，其他次数从节点明细打开。
  • 验证记录只证明这次走到的分支；没走到的分支要用会走到它的数据另外验证。

没有选的方案

方案没有选的原因
一台 worker 同时开多个浏览器要改 Worker、协定与桌面 App，旧 App 要更新，电脑负载高；用户选了分给不同的 worker。
条件写在节点上（{{ }} 表达式）条件和分支的关系在画布上看不出来；「其他情况」也难表达。
重复的出参收成清单下游入参要是数组，只有 Python 节点接得了；大量数据改用 M7.3 的批量运行。
略过与次数存进数据库要数据库迁移，也可能和实际的运行结果不一致；从结果算就够了。
