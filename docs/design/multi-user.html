多用戶與內部系統

團隊共用與內部系統這兩個前提，對設計提出的具體要求。

多用戶

M8 實作（ADR 0025）；之前是單使用者
認證
本地帳號（密碼用 scrypt 雜湊）；帳號表預留 provider、subject 給之後的 OIDC 與 LDAP（公司的 AD 或 SSO）。管理 Portal 的頁面與 API 一律要登入；第一個系統管理員只能在伺服器那台電腦上（127.0.0.1 的 /setup，或 rpa user create --admin）建立。裝置配對、Worker 與錄製端的權杖、Agent API 的金鑰照舊。
權限
以「領域」為單位：每個領域的成員是管理員、編輯者、執行者或檢視者，管的是那個領域的場景、組合場景、執行、批次與回看。看不到的領域不出現在清單裡，直接打開網址是 404。專案只是組合場景的分組，不管權限。
Secrets
AES-256-GCM 加密存放（金鑰在資料目錄的 secrets.key 或環境變數 RPA_SECRETS_KEY，要和資料一起備份）。Secrets 是全域的，只有系統管理員能設定與刪除；場景與登入角色照名稱引用，任何人都讀不出明文。只送到需要它的 worker 或錄製端。
稽核
登入、登出、登入失敗，以及每一個改變東西的請求（誰、何時、哪個路徑、結果），只增不改，每一筆串成雜湊鏈：改了或刪了中間任何一筆，驗證時就看得出來。系統管理員在「管理後台 › 稽核紀錄」查看。
版本
場景每次儲存產生不可變的新版本；執行紀錄指向確切版本。版本、驗證與發布紀錄都在領域資料夾，可以經由 git 審閱（M11）。
資料庫
正式環境用 PostgreSQL，支援多個 worker 與併發寫入；SQLite 只用於開發與原型（單機、單一程序），見 ADR 0008。
Runner 無狀態
從 M2 起只接收場景、入參與 Secrets，輸出結果與產物；放進 M3 的背景 worker、M9a 的遠端 worker 與 M10 的 Worker App 時都不用改。

內部系統帶來的要求

情況對策落在
目標系統只能從內網存取平台與 worker 都部署在內網；worker 與錄製端必須能直連目標系統，只有它們連伺服器、伺服器不連它們M9a、M10
每次執行都要登入每個角色保存並重用自己的登入狀態（Playwright storage state），減少登入次數、降低帳號鎖定的風險；登入失效時回報 needs_login，引導人工重新登入後續跑M4
老系統缺少語意化標籤定位器更依賴 css、xpath 與文字；錄製器避開自動生成的 id，產出穩定的選擇器M1、M4
iframe定位器以 frame 指定元素所在的 iframe（可巢狀），見 DSLM7a
點擊開出的新分頁（彈出視窗）開出新分頁的步驟寫 popup，在新分頁上的步驟寫 page，見 DSLM7b
自己開的新分頁DSL 提供開新分頁的步驟M7
檔案上傳（匯入 Excel、上傳圖片）入參的 type: file 與 upload 步驟；檔案在執行時上傳或用場景附件，見 DSLM7c
檔案下載download 動作；下載檔作為產物保存M7
表格資料抽取extract 支援表格轉成結構化資料M1
自簽憑證場景層級可設定忽略 HTTPS 錯誤，預設關閉並在審核時標示M2
頁面內容可能敏感AI 生成可切換到自架模型；截圖、錄影與回看依領域的權限存取M5、M8
錄製、調試與人工登入的瀏覽器開在錄製者自己的電腦：M4 時是執行平台的那台，M10.2 起是透過錄製端 App 操作時的那台錄製端，伺服器可以沒有螢幕。遠端瀏覽器畫面串流不做（ADR 0014）。測試網站（M2）先沿用 MVP 原型的本機測試頁，之後擴充成典型內部系統：登入、選單、iframe（M7a 的 /frames）、表格與檔案下載。
