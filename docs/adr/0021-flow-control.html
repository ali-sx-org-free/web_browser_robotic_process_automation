ADR 0021：場景內的流程控制是 DSL 的區塊步驟，契約與發布門檻不變

條件、迴圈與錯誤處理寫成步驟裡的區塊（if、forEach、repeat、try），條件沿用 expect 的寫法；重試只用於沒有副作用的動作；步驟紀錄依執行順序、以場景檔的路徑對應定義。出參仍只在獨立斷言通過後發布。

背景

場景的步驟原本是一層清單，從頭到尾直線執行，某一步失敗就停。真實系統常有「有時跳出的公告」「一張表逐列處理」「翻頁直到最後一頁」「選填的部分失敗也要繼續」「報表要等一下才完成」。MVP 時這些交給 Python 腳本（ADR 0010），但腳本失去 DSL 的校驗、逐步調試、步驟回看與審閱的可讀性。

路線圖的 M7 是流程能力；iframe、點擊開出的新分頁、上傳已提前做完（M7a～M7c），下載由 Python 節點補上。DSL 文件一直寫著「重試只用於沒有副作用的步驟」。

決策

  • 區塊步驟。if（condition、then、else）、forEach（items、as、steps）、repeat（times／while／until，條件模式必填 max）、try（steps、catch）。區塊也是步驟：有 id，可以 onError；逾時、分頁寫在裡面的步驟。
  • 條件沿用 expect。元素、頁面的檢查欄位與 expect 相同，加上 expression（Jinja 沙箱的真值）、wait（預設 0，只看當下）、not。不成立不算失敗；判斷本身出錯算失敗，不默默走錯分支。
  • 變數與事實。迴圈變數以 as 命名，另有最內層的 loop；catch 裡有 error。範圍在校驗時檢查。迴圈裡的事實每輪覆蓋，append 才累積成清單。
  • 錯誤處理與重試。任何步驟可寫 onError: continue；retry 只用於 goto、waitFor、expect、extract、screenshot，點擊、填寫等有副作用的動作要重複就明確寫成 if 或 try。總期限、紀錄上限不能被接住或繼續。
  • 結果仍由獨立斷言決定。有失敗後繼續或被接住的失敗時，報告、回看、驗證結果顯示提醒，不擋發布。
  • 紀錄依執行順序、以路徑對應。最外層的步驟一開始列出，區塊裡的步驟執行到才插在區塊後面，多了 path、parent、iteration 等欄位；回看、匯總報告、逐步調試都以 path 對應場景快照。上限：每個迴圈 1,000 項／輪、巢狀 5 層、每次 10,000 筆紀錄。
  • 自己開的分頁。openPage（as、url）、closePage（page），和 M7b 的 popup 共用名稱。
  • 相容。新欄位都是增加的，schemaVersion 維持 1；用到的場景標上擴充 flow，舊的錄製端與 Worker 不會領到。

後果

  • 常見的分支、逐列處理、翻頁與選填步驟可以留在 DSL，照樣校驗、調試、回看；Python 節點仍是逃生門。
  • 步驟紀錄不再和場景檔的步驟一對一：讀紀錄的地方要用 path（沒有 path 的舊紀錄依順序對應）。
  • 逐步調試要處理「迴圈裡的一步用哪一項」：調試頁可以選目前項，catch 裡的 error 是示範值。
  • 條件與迴圈錄不出來，要在 YAML 裡寫；場景編輯頁有範本，之後 M5 的 AI 可以產生。
  • 一次執行可能有很多筆紀錄：步驟截圖仍最多 500 張，紀錄超過上限算失敗，大量資料改用批次執行（M7.3）。

沒有選的方案

方案為什麼不選
流程都寫在 Python 節點失去 DSL 的校驗、逐步調試與步驟回看；運行環境模式不能開瀏覽器（ADR 0020）。
用 Jinja 的 if、for 在執行前展開步驟展開時頁面還沒打開，判斷不了畫面上有什麼；展開後的步驟和場景檔對不上。
每一步加 when 取代 if 區塊多步的分支要每步重寫條件；之後常用可以另加成 if 的簡寫。
點擊也可以自動重試送出表單重複會重複建單，違反「只重試沒有副作用的步驟」。
迴圈裡的事實自動變成清單單值也變清單、容易誤用；用 append 明確表示要累積。
組合場景層級的條件、迴圈、平行一起做那是節點之間的流程（M6 原型留下的另一組問題），另等決定。
