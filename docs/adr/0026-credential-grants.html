ADR 0026：登入角色與 Secrets 綁定到帳號與 API 用戶端才能用

領域的四種角色決定能對場景做什麼；登入角色與 Secrets 另外要綁定，綁定的帳號與 API 用戶端才看得到、用得到。系統管理員不受限制。

背景

登入角色是目標系統裡的一個身分（例如「測試網站：主管」），加上伺服器保存的登入狀態；用它的人就是以那個身分操作目標系統。M8 只看場景所在領域的角色：甲領域的編輯者在場景寫 login: { role: 乙領域的角色 }，就能用乙領域保存的登入狀態。Secrets 也一樣：任何編輯者都能在場景宣告一個 Secret，再把值填到自己控制的網頁。

主流 RPA 平台的憑證保管庫把「管理憑證」和「使用憑證」分開授權（例如 UiPath 的憑證資產、Automation Anywhere 的 Locker），這裡照同樣的想法。

決策

  • 綁定。credential_grants 記哪個登入角色或 Secret 綁定給哪個帳號（user:帳號 id）或 API 用戶端（client:代號）。領域的四種角色不變；同一個領域裡的角色仍是一層包一層。
  • 誰指定。登入角色由所在領域的管理員與系統管理員指定；全域的登入角色與 Secrets 由系統管理員。帳號不能自己認領。在「登入與憑證」每一列的「誰能用」加上或移除帳號、API 用戶端。
  • 看得到。登入角色的清單只列綁定的，加上自己是管理員的領域裡的（才能指定誰能用）；Secrets 只列綁定的名稱。API 用戶端的 GET /roles、GET /secrets 也只列綁定的。
  • 用到的地方都檢查。場景的登入角色與 Secrets：存檔、發布、驗證、執行、重跑、批次（建立、開始、重跑、每排一列）、組合運行（開始、每個節點）、逐步調試、錄製（選了登入角色或接著錄製）。子場景必須用同一個角色、Secrets 也要宣告在呼叫的場景（ADR 0023），所以看呼叫的場景就夠。登入角色本身：人工登入、登出、檢查要已綁定而且在那個領域至少是執行者；修改、刪除要已綁定而且是編輯者；自動登入用到的 Secrets，存檔的人要已綁定。用登入角色自動登入時不必另外綁定它用到的 Secrets。沒有權限時 403（login_role_forbidden、secret_forbidden），場景頁的「執行前要準備」先標出來。
  • 背景排的看開始的人。批次與組合運行記下開始或重跑的帳號（user_id；API 用戶端用原有的 client_id），之後排的每一列、每個節點用他檢查：中途取消綁定或停用帳號，還沒開始的就失敗。沒有人的背景工作（git 同步、匯入範例、錄製轉換）不檢查。
  • 系統管理員不受限制。能看能用全部，照 ADR 0025 留稽核紀錄。
  • 新建的登入角色綁定給建立的人。
  • 升級。升級後第一次啟動，把既有的 API 用戶端綁到它可用領域裡的登入角色（全域的也算）與所有 Secrets，稽核紀錄記一筆，只做一次；讓升級前能跑的照樣能跑。帳號不自動綁定。
  • 刪除。刪除登入角色、Secret、API 用戶端時一併刪除綁定。

後果

  • 升級後只有系統管理員能用登入角色與 Secrets，直到指定其他帳號；這是預期的（M8 合併到這次之間沒有發布版）。
  • 跨領域引用登入角色（ADR 0015 的 requires）照樣可以：能不能用看綁定，由登入角色所在領域的管理員決定。評估時建議過「只能用同一個領域或全域的登入角色」，實作時發現會打破 ADR 0015 已有的跨領域依賴，而綁定已經擋住原本的問題，所以不加這條限制。
  • 看得到場景的人仍看得到場景檔裡寫的登入角色代號與 Secret 名稱（只是名稱，沒有值與登入狀態）。
  • 執行的截圖、錄影與回看照 ADR 0025 依領域的權限，不另外看綁定。

沒有選的方案

方案沒有選的原因
只靠領域的角色就是這次要補的問題：登入角色與 Secrets 跨出它們所在的領域。
只綁定登入角色，Secrets 不管編輯者仍能在場景直接引用 Secret、把值填到別的網頁。
只在執行時檢查沒綁定的編輯者照樣能寫步驟，再讓綁定的人去跑；所以存檔與調試也檢查。
帳號自己認領、管理員核准多一道流程；第一版由管理員直接指定，之後需要再加。
群組目前人數不多，直接綁定帳號；群組之後再做。
