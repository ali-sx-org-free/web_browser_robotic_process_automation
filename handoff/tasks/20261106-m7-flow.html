1. 結論

  • 可以做，不需要新的外部元件。步驟的資料模型（Pydantic 的 discriminated union）可以直接遞迴：區塊步驟裡再放步驟，校驗、錯誤位置與 JSON Schema 都照常運作（第 3 節實測）。
  • 做法：新增四種區塊步驟和幾個欄位。if（條件）、forEach（對清單逐項做）、repeat（重複，次數或條件）、try（出錯時改走補救步驟）；每一步可以寫 onError: continue、無副作用的步驟可以寫 retry；openPage／closePage 自己開關分頁；extract 多一個 append 讓迴圈累積資料。
  • 契約與發布門檻不變。出參仍只在獨立斷言 verify 通過後發布；沒有用到新欄位的場景，雜湊與執行結果完全不變，schemaVersion 維持 1。舊的錄製端與 Worker 看不懂時，沿用 M7a 起的擴充機制提示更新。
  • 分三期（D1）。M7.1 流程控制（上面那些）；M7.2 子場景（在同一個瀏覽器裡呼叫另一個已發布的場景）；M7.3 資料驅動（一張表的每一列各跑一次、各有報告）。建議先做 M7.1，確認後再細化後兩期。
  • 要你決定的有九項（第 11 節），都附了建議。最需要看的是條件怎麼寫（D2）、迴圈裡的資料怎麼累積（D3）、哪些步驟可以重試（D5）、資料驅動是「批次執行很多次」還是「一次執行裡逐列做」（D9）。

4. 設計：M7.1 流程控制

4.1 新增的動作與欄位

寫法做什麼關鍵欄位

4.2 條件（D2）

if 的 condition、repeat 的 while／until 用同一種條件，寫法沿用 expect：熟悉 expect 就會寫條件，差別只是「不成立不算失敗」。

  • 元素：target 加上 state（visible、hidden、enabled、disabled、checked、unchecked、editable，另加 attached、detached）、text、value、count 其一，match 同 expect。
  • 頁面：沒有 target 時 url 或 title。
  • 資料：expression: '{{ … }}'，結果是真值就成立（入參、事實、迴圈變數都能用）。
  • wait：最多等多久讓條件成立（毫秒）；預設 0，只看當下。成立就馬上結束，不必等滿。
  • not: true：反過來判斷。page：在哪個分頁判斷，同步驟的 page。
  • 判斷本身出錯（例如定位器寫法讓 Playwright 報錯、{{ }} 引用不存在的值）算這個區塊失敗，不當成「不成立」，避免寫錯而默默走錯分支。
- id: close-notice
  name: 有系統公告就關掉
  action: if
  condition:
    target: { role: dialog, name: 系統公告 }
    state: visible
    wait: 2000                      # 最多等 2 秒；沒出現就走 else（這裡省略）
  then:
    - id: close-notice-button
      action: click
      target: { role: button, name: 關閉, within: { role: dialog } }

4.3 迴圈、迴圈變數與事實（D3、D4）

  • forEach 的 items 求值後要是清單：type: array 的入參、extract 的 multiple 或 get: table 的事實都可以。不是清單時這一步失敗；空清單執行零次、照樣通過。
  • 迴圈變數：as: order 之後，迴圈裡用 {{ order.title }}；另外 {{ loop.index }}（第幾項，從 1 開始）、{{ loop.count }}（共幾項，repeat 的條件模式沒有）、{{ loop.first }}、{{ loop.last }} 指最內層的迴圈。名稱不能和 inputs、secrets、facts、env、loop、error 或外層的迴圈變數相同。
  • 事實：迴圈裡 extract 的事實每一輪覆蓋，迴圈結束後是最後一輪的值；要累積就寫 append: true，事實是清單、每輪加在後面。好幾步可以寫同一個 as，條件是它們都寫了 append。
  • 分支與迴圈裡產生的事實：校驗時當成之後「可能」有值，不擋；執行時真的沒有值（例如那個分支沒走到）就在用到它的那一步失敗，錯誤說明是哪一步產生、這次沒有執行。
  • 上限（D4）：forEach 最多 1,000 項、repeat 的 times 與 max 最多 1,000；用 while／until 一定要寫 max，到了還沒結束算失敗（不會默默停下）；區塊最多巢狀 5 層；一次執行最多 10,000 筆步驟紀錄，超過算失敗。每一步的截圖沿用現在的 500 張上限，錄影完整。每一輪都受總期限 deadline 限制。
inputs:
  orders: { type: array, description: 要建立的訂單，例如 [{"title": "A", "qty": 2}] }
steps:
  - id: each-order
    action: forEach
    items: '{{ inputs.orders }}'
    as: order
    steps:
      - { id: new-order, action: click, target: { role: button, name: 新增 } }
      - { id: fill-title, action: fill, target: { label: 標題 }, value: '{{ order.title }}' }
      - { id: fill-qty, action: fill, target: { label: 數量 }, value: '{{ order.qty }}' }
      - { id: save-order, action: click, target: { role: button, name: 儲存 } }
      - { id: read-id, action: extract, target: { testId: record-id }, as: recordIds, append: true }
outputs:
  recordIds: { type: array, from: '{{ facts.recordIds }}' }
# 翻頁抽出全部的列：第一頁先抽，之後「下一頁」可以按就繼續
  - { id: first-page, action: extract, target: { css: 'table#list' }, get: table, as: rows, append: true }
  - id: next-pages
    action: repeat
    while: { target: { role: button, name: 下一頁 }, state: enabled }
    max: 50
    steps:
      - { id: next, action: click, target: { role: button, name: 下一頁 } }
      - { id: wait-list, action: waitFor, loadState: networkidle }
      - { id: more-rows, action: extract, target: { css: 'table#list' }, get: table, as: rows, append: true }

4.4 錯誤處理與重試（D5、D6）

  • try／catch：steps 其中一步失敗就停下、執行 catch；catch 裡可以用 {{ error.step }}（失敗那一步的 id）與 {{ error.message }}。catch 全部通過時整個 try 算通過、繼續後面的步驟；catch 也失敗就整次執行失敗。總期限到了、使用者取消不會進 catch。
  • onError: continue：任何步驟（含區塊）都能寫。失敗照樣記成失敗，接著執行下一步。
  • 結果怎麼算（D6）：有「失敗後繼續」或被 catch 接住的步驟時，執行的結果仍由獨立斷言 verify 決定；報告、運行頁與發布前的驗證結果多一行黃色提醒「N 步失敗後繼續」，不擋發布。
  • retry（D5）：只能寫在沒有副作用的動作：goto、waitFor、expect、extract、screenshot。點擊、填寫、選擇、勾選、按鍵、上傳、下載、開關分頁與區塊都不行，寫了校驗時指出——這是路線圖與 DSL 文件原本的規則（Runner 與逐步調試也把填寫、勾選當成有副作用）。times 1～5、delay 預設 1000 ms；每次嘗試各有這一步的逾時，全部都在總期限內。紀錄寫第幾次成功，前幾次的錯誤列在提醒。
  • 要「點了沒反應就再點」的情況，用 if 或 try 明確寫出來，讓重複點擊這件事看得到、審得到。
  - id: optional-survey
    action: try
    steps:
      - { id: open-survey, action: click, target: { text: 填寫滿意度問卷 } }
      - { id: submit-survey, action: click, target: { role: button, name: 送出 } }
    catch:
      - { id: survey-failed-shot, action: screenshot, file: survey-failed }
      - { id: back-home, action: goto, url: / }
  - id: wait-report-ready
    action: expect
    target: { testId: report-status }
    text: 已完成
    timeout: 10000
    retry: { times: 3, delay: 5000 }

4.5 自己開的新分頁

  • openPage 在同一個瀏覽器工作階段（同一個登入狀態）開新分頁，以 as 取名；寫了 url 就順便打開（以 / 開頭時接在 baseUrl 後面）。之後的步驟用 M7b 的 page 指定它。
  • closePage 關掉 page 指定的分頁；一開始的分頁不能關。關掉之後的步驟不能再用這個名稱（線性的部分校驗時就指出，分支裡的在執行時指出）。
  • 分頁名稱和 M7b 的 popup 共用同一組名稱，不能重複。錄製稿的 page1 = context.new_page() 轉成 openPage，page1.close() 轉成 closePage。
  - { id: open-report, action: openPage, as: report, url: '/reports?month={{ inputs.month }}' }
  - { id: read-total, action: extract, page: report, target: { testId: total }, as: total }
  - { id: close-report, action: closePage, page: report }

4.6 校驗規則（rpa validate、Portal 存檔、rpa pack check 相同）

  • 步驟 id 在整個場景（含所有巢狀的步驟）唯一。
  • 區塊步驟（if、forEach、repeat、try）不能寫 timeout、page、popup；裡面的步驟各自寫。then、steps、catch 至少一步；else 可省略。
  • 條件的欄位規則同 expect（元素檢查與頁面檢查不能混用、match 只用於文字比對、正規表示式要能編譯）；expression 與其他欄位擇一。
  • {{ }} 的範圍：迴圈變數與 loop 只在那個迴圈裡；error 只在 catch 裡；facts 的「之前」依執行順序推算，分支與迴圈裡產生的算「之後可能有」。
  • retry 只能寫在第 4.4 節列的動作；append 只能寫在 extract；同名事實的每一步都要 append。
  • 上限見第 4.3 節；超過時指出那一層、那個欄位。

4.7 執行（Runner）與紀錄

  • Runner 遞迴執行步驟；每一步的逾時、總期限、取消照舊。{{ }} 仍在執行那一步之前才代入，多了迴圈變數與 loop（catch 裡多 error）。
  • 步驟紀錄（steps.json）改成依執行順序：一開始只列最外層的步驟（狀態「略過」），區塊裡的步驟執行到才新增，緊接在它的區塊後面。每筆多幾個欄位，沒用到新語法的場景這幾個欄位都是預設值： path（定義在場景檔的位置，例如 ["steps", 2, "steps", 1]，回看用它找原文與定位器）、 parent（外層區塊是第幾筆紀錄；Python 節點已經用 parent 表示巢狀，章節只取最外層的規則不變）、 iteration（第幾輪）、attempts（重試的次數）、continued（失敗後繼續）、 branch（if 走了 then 或 else）、iterations（迴圈共跑幾輪）、caught（try 接住的步驟與錯誤）。
  • 自動化日誌：巢狀的步驟縮排，標出「第 3 步 › 第 2 項 › 第 1 步」；條件寫出判斷結果與等了多久，重試寫出第幾次。
  • 報告與回看：步驟清單依巢狀縮排、迴圈每一輪可以收合；時間軸的章節仍是最外層的步驟，迴圈的章節裡依輪分段；點巢狀的步驟照樣跳到影片的那個時間、顯示那一步的原文。組合運行的匯總報告與合併回看（ADR 0019）用同一份紀錄，不另做。
  • 失敗時停在哪：回看打開時停在第一個「沒有被接住」的失敗步驟之前；被 catch 接住、onError: continue 的失敗標黃色。

4.8 逐步調試（D7）

  • 步驟清單變成可以展開的樹。區塊可以整塊執行（照 Runner 的規則判斷條件、跑迴圈），也可以單獨執行裡面的一步。
  • 單獨執行迴圈裡的一步時，迴圈變數用「目前這一項」：預設第 1 項，可以在迴圈那一列切換；items 在第一次需要時求值。catch 裡的一步單獨執行時，error 是一個示範值。
  • 「有副作用、執行過的步驟要確認才重跑」照舊；區塊裡有任何有副作用的步驟，整塊就算有副作用。「執行到這裡」只用於最外層的步驟。
  • Agent API 的 POST /agent-api/v1/debug/{id}/steps/{index} 保持原意（最外層第幾步）；多一個請求內容 path 執行巢狀的步驟。

4.9 相容性與 Portal

  • 新欄位都是增加的，schemaVersion 維持 1；沒用到的場景雜湊不變、不用重新發布。
  • 擴充 flow：用到第 4.1 節任何一項的場景標上它；0.8.x 以前的錄製端與 Worker 不會領到這種任務，執行頁說明要更新哪個 App（和 M7a 起的做法相同）。
  • Portal 的場景編輯仍是 YAML（自動化步驟一段），JSON Schema 跟著更新；步驟編輯區多一個「插入」選單，放 if、forEach、repeat、try、openPage 的範本。
  • 條件與迴圈錄不出來：先錄成直線的草稿，再把需要的部分包進區塊。之後 M5 的 AI 可以直接產生。

5. M7.2 子場景（概要，D8）

在一個場景的步驟裡呼叫另一個已發布的場景，在同一個瀏覽器、同一個分頁裡接著做。和組合場景（M6）的差別：組合場景的每個節點各自開瀏覽器、各自執行；子場景共用登入與畫面，適合「先建客戶、再在同一個畫面建訂單」這種拆開重用的步驟。

  - id: create-customer
    action: call
    scenario: CUST-001          # 已發布的場景代號
    revision: 4                 # 固定版本，只能是發布過的
    inputs: { name: '{{ order.customer }}' }
    as: customer                # 子場景的出參 → {{ facts.customer.customerId }}
  • 契約不變：子場景的入參照它的契約校驗；它的步驟跑完後立刻跑它自己的 verify，通過才把出參交回呼叫的場景。
  • 子場景要是 DSL 場景（不是 Python 節點）；登入角色要和呼叫的場景相同，或子場景不需要登入。不能遞迴呼叫，最多 3 層。
  • 固定版本的子場景算進呼叫場景的雜湊與快照：子場景出新版本時，呼叫的場景要改 revision、重新驗證才會用到。領域資料夾與 git 同步（ADR 0015）沿用組合場景的跨領域依賴處理。
  • 報告與回看裡，子場景的步驟縮排在 call 這一步下面。

6. M7.3 資料驅動（概要，D9）

建議把「資料驅動」做成批次執行：選一個已發布的場景（或專案裡的組合場景），上傳 CSV／Excel 或貼一張表，每一列是一組入參，每一列各自是一次執行，各有驗證、報告、出參與回看。和 forEach（一次執行裡逐項做）分工：

批次執行（M7.3）forEach（M7.1）
一列失敗只影響那一列，其他照跑；可以只重跑失敗的列整次執行看 try／onError 怎麼寫
結果每列一份報告與出參，加一頁匯總（可以匯出成 CSV／Excel）一份報告，出參可以是清單
適合幾十到幾百筆、每筆都要證據（例如逐筆建單）同一個畫面裡逐項處理（例如勾選清單裡的每一項）
  • 欄位名稱對應入參名稱，對不上時在畫面上對應；開始前逐列校驗，有問題的列先列出來。
  • 選項：失敗時繼續或停下；同時跑幾列（受可用的 Worker 限制，同一台一次一列）。
  • 伺服器多兩張表（批次與每一列），要一個資料庫遷移；Agent API 多一個建立批次、讀結果的端點。

12. 沒有選的方案

方案為什麼不選
流程都寫在 Python 節點相容模式的 Python 節點可以用 Playwright 做任何事，但失去 DSL 的校驗、逐步調試、步驟回看與審閱的可讀性；運行環境模式不能開瀏覽器（ADR 0020 的 D2）。仍是逃生門，不是 M7 的做法。
用 Jinja 的 {% if %}、{% for %} 在執行前展開步驟展開時頁面還沒打開，判斷不了「畫面上有沒有公告」；展開後的步驟和場景檔對不上，回看與調試都難。
每一步加 when: 取代 if 區塊單一步驟的條件比較短，但多步的分支要每步重寫一次條件。之後若常用，可以另加成 if 的簡寫。
只有 onError: continue，沒有 try做不了「失敗時先截圖、回首頁，再繼續」這類補救。
迴圈的 break、continuewhile／until 與 if 已經寫得出常見的情況（第 4.3 節的翻頁）；之後真的需要再加。
點擊也可以自動重試違反路線圖「重試只用於無副作用的步驟」；送出表單重複兩次會重複建單（D5 的其他選擇保留明確標示的版本）。
組合場景層級的條件、迴圈、平行一起做那是 M6 原型留下的另一組問題（節點之間的流程），和場景內的流程不同；另等決定，不放進 M7。
