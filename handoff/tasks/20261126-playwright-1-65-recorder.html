Playwright 1.65 的接著錄製

進度、決定與下一步

  • 原因：1.65 的 Python 端改成產生的 protocol_channels，Channel 沒有通用的 send；原本的 enableRecorder 改名 showRecorder，由 BrowserContext._show_recorder(params) 送出（codegen 也這樣開始錄製）。pyright 報 record.py:71；執行時接著錄製在既有步驟跑完、開始錄製那一刻送出 error 事件：AttributeError: 'BrowserContextChannel' object has no attribute 'send'（新測試在舊寫法上重現）。
  • 已完成：enable_recorder 改成 context._sync(impl._show_recorder(params))，參數不變（language、mode、outputFile、handleSIGINT）。新的 test_record_browser.py（角色 recorder，Linux 的 PR 每次都跑 Chromium）：(1) 直接在開好的 context 上開始錄製，錄製稿只有之後的操作；(2) 整個 record.main：執行 BA-001 既有的 7 步、開始錄製、使用者操作後關掉分頁，結束碼 0、事件依序 replaying、recording，錄製稿不含既有步驟填的標題。Inspector 用 Playwright 自己測試用的 PWTEST_CLI_HEADLESS=1 改成無頭，沒有螢幕也能跑；第 (2) 個另把瀏覽器換成無頭、以測試代替使用者的操作與關視窗。
  • 錄影取消的測試：main 上 Windows 的 Worker 測試，CI #121 test_cancelled_run_keeps_a_playable_video[chromium]（video.json 的 error 是 unreadable）與 test_each_step_has_a_screenshot[chromium]（兩步之間 1.46 秒，上限 1 秒）失敗；CI #122 這兩個通過，改成 test_too_many_records_cannot_be_continued[firefox] 的 goto 逾時；1.65 上的 CI #114（deps/uv-upgrade 手動觸發）與 #123（PR #37）Windows 都通過。看起來是 Windows 上時好時壞，不是每次都壞；1.65 是否讓它更常發生沒有足夠的次數判斷。這次只讓取消測試失敗時印出整份 video.json（原本只印 dict，被 pytest 截斷，看不到大小與終止的經過）。
  • 未完成／阻礙：(1) Windows 錄影取消偶發 unreadable 的根因未查（要 Windows 才能重現，下次失敗時看完整的 video.json）。(2) 本機的影片相關測試在容器的 Chromium 158 上全部失敗（影片資料夾是空的），是瀏覽器版本不符的環境問題，不代表 CI；Linux 的完整範圍（main 推送的 Python 3.12）在 1.65 上通過。(3) 打包版的自我測試不涵蓋接著錄製（設計頁原本說會），已在設計頁更正，沒有補到自我測試。
  • 決定：實作選擇（Claude）：沿用 1.65 的私有 API，不固定回 1.64；理由是改動只有一行、行為和 codegen 相同，並由新的測試在下次升級時發現。1.65 另有 startRecording／stopRecording（不開 Inspector、以事件回傳程式碼），同樣是私有 API，這次不換。
  • 下一個具體動作：使用者審閱、合併 PR。之後在錄製端實際「接著錄製」一次（人工驗收）。
  • 未提交／stash／ignored 產物：無。
