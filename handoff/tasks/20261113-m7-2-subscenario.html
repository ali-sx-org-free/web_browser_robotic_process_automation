M7.2 子場景（call）

場景用 action: call 在同一個瀏覽器、同一個分頁裡接著執行另一個場景的固定版本：入參照子場景的契約、它自己的獨立斷言通過才交回出參。子場景那個版本的場景檔跟著呼叫場景的版本存放（calls/）、算進內容雜湊。設計見 ADR 0023，寫法見場景 DSL › 子場景。

#項目選擇
I1子場景檔放在哪裡子場景那個版本的場景檔原樣複製到呼叫場景的版本目錄 calls/<代號>/<版本>.yaml（子場景自己呼叫的也平放），算進雜湊。M7 任務紀錄原本寫「沿用組合場景的跨領域依賴處理」；改成跟著版本存放，呼叫場景自己就完整，Worker、錄製端、rpa run 與 git 同步都不用另外處理。
I2伺服器什麼時候檢查「發布過」存檔時：新加的 call 要引用發布過的版本（規則同組合場景的節點）。上一個版本已經帶進來的子場景不再檢查，子場景之後封存或這台沒有它，呼叫場景照樣能改別的地方再存。送來的 calls/ 檔案不直接採用，這台有那個版本時一律用這台的。
I3第一版的其他限制子場景用到的 Secrets 呼叫場景也要宣告；不能有 type: file 的入參與出參；最多 10 個不同的子場景版本；不能直接或間接呼叫自己（不管版本）。都在校驗時檢查。
I4迴圈裡逐筆呼叫append: true 把每一次的出參累積成清單（同 extract 的 append，D3）；沒寫時每次覆蓋。
I5各自獨立與沿用的部分事實、迴圈變數、分頁名稱各自獨立；子場景開了沒關的分頁結束時關掉；截圖檔名前面加 call 的 id。瀏覽器、登入狀態、總期限、紀錄上限沿用呼叫場景；網址：執行時指定了就全部用它，否則子場景用自己的 baseUrl，沒寫用呼叫場景的。
I6timeout 與 retrycall 不能寫 timeout（子場景裡的步驟各自決定），不能 retry（子場景多半有副作用）；可以 onError: continue、可以被 try 接住。
I7逐步調試與錄製逐步調試時 call 是一步、整個子場景一起執行、算有副作用；子場景檔由伺服器包成 JSON 交給子程序（換版本的 load 命令也帶）。接著錄製（先重播既有步驟）還不支援用到 call 的場景，直接說明。
I8相容性擴充 call；派工與調試前連同子場景用到的擴充一起比對，0.9.x 以前的 App 領不到。schemaVersion 維持 1；沒用到 call 的場景雜湊不變。

  • 子場景失敗時呼叫的場景停下：呼叫場景加一個入參 title，call 的 inputs 寫 title: '{{ inputs.title }}'；用標題只有空白執行：call 失敗（BA-001 的入參不符合 pattern），子場景一步都沒做，後面的步驟略過。把 call 包進 try 時改走 catch，後面的步驟照常執行。
  • 子場景出新版本不影響：改 BA-001（例如數量的預設值）存成第 2 版並發布；呼叫場景已發布的版本照樣用第 1 版（版本檔案不變、重新執行結果相同）。呼叫場景改成 revision: 2 存檔，才帶入第 2 版。
  • 只能用發布過的版本：call 一個沒發布過的版本，存檔回錯誤「沒有發布過」；封存 BA-001 後，已經用到它的呼叫場景照樣能改名再存，新的場景加 call BA-001 被擋。
  • 逐步調試：call 那一步整個子場景一起執行、畫面接著在同一個分頁；再執行一次要確認（有副作用）。
  • 舊版 App：用 main 的 worktree 開 v0.9.x 的 Worker，用到 call 的場景不會派給它，運行說明要更新 App。
  • 接著錄製：用到 call 的場景按「接著錄製」，直接說明還不支援。
