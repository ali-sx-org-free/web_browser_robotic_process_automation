原因

  • 失敗的運行：每晚完整測試 run 42933251106（排程，2026-11-10 16:40 America/Los_Angeles（PST，UTC−08:00）開始，main ab15ce6），只有「完整測試（ubuntu-latest，Python 3.13）」第 1 遍失敗（1 failed、2371 passed、6 skipped），同一台機器的瀏覽器測試第 2、3 遍與 Python 3.12、macOS、Windows 都通過。失敗的是 test_video_lines_up_with_the_steps[firefox]：點擊開始前 0.3 秒是白色（對），點擊結束後 0.3 秒還是白色 [255, 255, 255]（應該是紅色）。
  • 錄影怎麼拿到畫面（Playwright 1.64 的原始碼）：Firefox 的 Juggler（nsScreencastService.cpp）在每次合成畫面時截一格；已經有 1 格送出、還沒收到 Playwright 的確認時，這次的畫面直接丟掉（kMaxFramesInFlight = 1），不會補送。無頭模式只有頁面重畫才有新的一格。Chromium 由 Playwright 設 maxFramesInFlight: 5，比較不容易丟。
  • 第一次的判斷（PR #19，已被 issue #21 推翻）——測試頁為什麼容易中：本機用第二個 screencast 訂閱記下每一格的時間（Chromium，原本的測試頁）：點擊前後只有 3 格（點擊結束前 13 毫秒、2 毫秒，第二格才是紅的），下一格要到 1.49 秒後 #done 出現。也就是整個「變紅」只靠一格；Firefox 那一格在途時剛好遇到點擊造成的重畫（滑鼠移入、按下、變紅相隔十幾毫秒），或主執行緒忙（例如每一步做完的截圖）而晚確認，就會被丟掉，影片一直是白的到 1.5 秒後。和 20261029-replay-chapters 在本機看到的偶發失敗（Chromium 的分頁測試，點 main-red 後 0.3 秒還是白的，約 86 次 2 次）是同一個情境。
  • 另一個可能的因素（未證實、這次沒有改）：Firefox 每一格的時間是「Firefox 程序啟動後幾秒」，Playwright 用第一格送到 Node 的時間換算成實際時間（_screencastClockOffset），第一格送得晚，整段影片的時間就偏後同樣多。這會讓變紅稍微晚於 0.3 秒，不會晚到 1.5 秒。新的失敗訊息會寫出實際晚了幾秒，可以分辨是哪一種。
  • issue #21 的證據（推翻第一次的判斷）：一鍵安裝腳本排程 run 43345289668（main 3437048，PR #19 合併後），「專案內執行（ubuntu-latest）」第一次 setup.sh 跑完整測試時同一個測試失敗（job 131623211344；Linux、Firefox、startedAtSource: file）。換算成影片時間：點擊從第 1.531 秒到 1.624 秒（93 毫秒），取樣在第 1.231 秒（白，對）與 1.924 秒（白 [255, 255, 255]，錯）。PR #19 加的診斷從第 1.324 秒起每 0.1 秒取樣，第 1.524 秒已經是紅色（點擊結束前 0.10 秒，甚至比步驟記下的點擊開始早 7 毫秒，在 0.3 秒的容許誤差內）。影片裡變紅的那一格沒有被丟掉，時間也沒有偏後；問題在「1.924 秒讀到白色」這一次。
  • 還沒排除的兩種可能：（一）讀影片的那一側：測試用 Chromium 的 <video> 跳到 1.924 秒、seeked 後立刻畫到 canvas，可能畫到的還是上一個取樣點（1.231 秒，白色）的那一格。本機用 Chromium 錄的影片、在 CPU 負載下各讀了 150 次與 200 次，都沒有讀到舊畫面；CI 上讀的是 Firefox 錄的影片。（二）影片本身：Firefox 錄的影片在紅色之後真的有一段白色的畫面。從 Playwright 1.64 與 Juggler 的原始碼找不到會這樣的機制，但沒有那支影片可以檢查。第一次加的小方塊不影響這兩種可能，保留。
